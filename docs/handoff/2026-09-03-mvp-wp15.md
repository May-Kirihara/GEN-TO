## 秘密監査の結果 (最重要報告)

**既存の泄漏経路は発見されなかった。** 確認した経路と根拠:

| 経路 | 監査結果 |
|---|---|
| APIキー → ログ/DB | `ApiKey` のDebug/Displayは構造型伏せ字 (`apikey.rs`)。`SecretStore` のエラー文は鍵を含まない。`AiClient` は鍵をAuthorizationヘッダに出すのみで `AiError` はヘッダ値を整形しない (reqwestエラーもURL+原因のみ)。`ai_runs.request_summary` は鍵を含めない設計 (既存テスト `api_keys_never_in_db` / `run_history_records_request_summary_without_secret`) |
| GPS → ログ | 全76+17箇所のtracing呼び出しを精査。GPS座標やメタデータ列を書式化する箇所は存在しない。`MetadataColumns` はderived Debugを持つが誰もログに出していなかった |
| panic → panic.log | payloadは任意の文字列を運び得るが、現状のpanicメッセージに鍵/GPSを含むものは無し |

**ただし「誰もログに出していない」は構造的保証ではない**ため、WP-15として
以下の防護を追加した (test-first):

1. `gento_core::redact` (新規module):
   - `redact_key`: 先頭4字+`****` (PM決定「api key類=先頭4字+マスク」)
   - `scrub_text`: Bearer/Authorization/sk-・rk-・ghp_・gho_系/api_key=値/
     **GPS座標らしい高精度小数 (整数1〜3桁.小数5桁以上 → `<coord>`**。
     4桁以下 (ヒット率・比率等) は誤爆対象外)
   - `scrub_paths`: 絶対パス → `<path>` (URLは保持)
2. **危険な構造体のDebug手動実装**: `MetadataColumns` (GPS列 → `<gps>`)、
   `AssetMetadataParsed` (raw_exif等の生JSONはGPS DMSを含み得るため
   バイト数要約 `<N bytes>` 表示に)。`{:?}` でログ混入した場合の構造的防護。
3. AIジョブ失敗時のwarnログを追加 (`run_one_job`。error文字列はscrub通し。
   それまでAI失敗はDB記録のみでログに observability が無かった)。
4. panic hook の payload を scrub。
5. **実証テスト** `ai_failure_log_never_contains_api_key_or_gps_even_at_debug`:
   鍵登録プロファイル + GPS列メタデータ + ルートsend_gps=ONでAIリクエストが
   500失敗したとき、debugレベル込みの全ログ出力に鍵素材・GPS座標が出ない。
   同時にmock endpointの受信記録で「鍵付きリクエストが送信され、GPS座標は
   endpointへ届いた」ことを正面証明 (「送っていないから出ない」の空振り排除)。

## 各要素の実装

### 1. 設定 (PM決定1: app_settings + migration禁止)

- `crates/gento-db/src/settings.rs` (新規): 型付きaccessor。
  `general.log_level` (error/warn/info/debug) / `cache.thumbs_max_bytes`
  (64MiB〜1TiB) / `settings.version` (=1) / `fts.last_rebuild_at` /
  既存 `backup.auto_full_db`・`backup.retention_generations` を同一枠で読み書き。
  新規キーはJSON値、backup系は従来の素の文字列 (既存コマンド互換)。
  **破損値/未知値 → 既定値 + `tracing::warn!` + corrupt_keysへ記録**。
  既定 `thumbs_max_bytes` = 2GiB = gento-image `DEFAULT_MAX_BYTES` と同値
  (報告: 現状挙動と同値。重複定義はtauri層テストで同値pin)。
- tauri `settings.rs`: `settings_get` / `settings_set_log_level` /
  `settings_set_thumbs_max_bytes` コマンド (DTO camelCase)。

### 2. ログ基盤 (PM決定4)

- tauri `logging.rs` (新規): stdout tee + **メモリring 512行** (bundle用) +
  `tracing_subscriber::reload` による実行時レベル変更。
  起動時 `GENTO_LOG` env優先 → 無ければ `general.log_level` 設定を適用。
  stdout形式は不変 (計測ドライバ互換)。
- **テスト工数メモ**: thread-local `set_default` は並行テストでcallsite
  interestが競合しイベントが静かに落る (tracing既知制限。単独pass・全体
  failの形で顕在化)。テストからのログ検証は `logging::test_capture()`
  (プロセスglobal capture subscriber + thread id仕分け) を使うこと。

### 3. キャッシュ (PM決定2)

- `ThumbnailCache::set_max_bytes` (max/targetを`CacheInner`へ移動):
  縮小時は即時LRU prune (target=95%)。起動時 (`ThumbnailService::
  new_with_limit`) と設定変更 (`settings_set_thumbs_max_bytes`) の両経路。
- **symlink安全の強化** (既存は緩かった): `clear()` はshard内の
  **通常ファイルのみ**削除 (symlinkは残す・リンク先に触わらない。
  旧実装は `fs::metadata` でリンク先サイズを会計していた)、
  `recover_startup` は `DirEntry::metadata` (no-follow) + file_type検査で
  symlinkを台帳登録しない。テスト: `clear_removes_regular_files_only_*` /
  `startup_recovery_ignores_symlinked_shard_entries` (リンク先実体の無傷を
  実証)。削除→grid要求→再生成は既存テストが担保。

### 4. 診断 (PM決定3)

- tauri `diagnostics.rs` (新規): `diagnostics_snapshot` (5領域、read-only。
  quick_checkのみFTS5内部書き込みのためwriter接続 — `Db::diagnose`と同一理由)。
  - DB: quick_check・schema_version・DB/WALサイズ・設定破損検知数
  - FTS: docs数・整合・**最終再構築時刻** (`fts.last_rebuild_at` を
    `fts_rebuild`/`fts_repair`/走査後自動修復の成功時に記録するよう追加)
  - USearch: 索引数 vs embeddings正本数・stale flag・次元
  - モデル: manifest検証状態 (verified/missing/missing_files/mismatch)・
    embedding_dim・license・worker phase・再起動回数
  - ジョブ: type×state別件数・最古pending経過秒 (RFC3339 parser自作 —
    chrono依存回避、ids.rs整形形式と往復テスト済み)
- テスト: 壊れたFTS (docs削除注入) のstale検出、jobs集計、破損設定カウント。

### 5. 診断bundle (PM決定5)

- `diagnostics_bundle_create(destDir)`: tmp書き→sync→原子rename
  (`gento-diagnostics-{RFC3339}.json`、衝突時連番)。内容: 各version・設定
  (鍵素材は構造的に不含)・診断スナップショット・ログ末尾100行 (ringから)。
- **三段redaction**: (1) JSONツリー全体を scrub_text、(2) 既知dirを

## 注意・申し送り

- **ログのGPS scrubはパターンベース** (小数5桁以上)。ログ設計上GPSは
  構造的に出ないため、これは迂回経路 (外部文字列混入) への保険。
  4桁以下の小数は対象外 (ヒット率等の誤爆回避) — 仕様として
  api-contract §49 に明記。
- bundleのログ末尾は「ring (＝redaction済みログ出力そのもの) から」取得。
  stdoutをファイル化してはいない (ログファイルは panic.log のみ)。
  ログファイルへの永続出力が欲しくなった場合は ring のファイル化を
  別WPで (計測ドライバのstdout grep互換に注意)。
- `settings_set_log_level` の実行時変更は `GENTO_LOG` env指定時も
  ユーザーの明示操作なら適用される (起動時のみenv優先)。
- usearch stale検出は件数差ベース。embedding serviceを起動した実環境での
  building中の観測は時変動するため、テストは内部整合 (stale == 件数差,
  ready⇒件数一致) で固定。
- `Cargo.lock` に変化なし (依存追加なし・feature追加なし)。
