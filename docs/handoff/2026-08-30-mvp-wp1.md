# MVP-WP-1 引き継ぎ: SQLite基盤とマイグレーション (2026-08-30)

## 変更内容 (意図ベース)

1. **`crates/gento-db` 新設** — SQLite基盤 (メタデータの正本):
   - `Db::open(path)` / `open_with(path, DbOptions)`: 親ディレクトリ作成、
     PRAGMA設定、migration適用まで。新規作成・既存オープン両対応
   - **並行性方針** (crate doc + architecture.md に文書化): 書き込みは
     単一writer接続を `Db::with_writer` がMutexで直列化。読み取りは
     `Db::with_reader` が分離接続 (WALなのでwriterをブロックしない。
     idle 2本保持、貸出集中時のみ追加接続を開き返却時に閉じる)。
     busy_timeout 5000ms、WAL、`foreign_keys=ON` (全接続)、
     `synchronous=NORMAL` (WAL+NORMALの標準推奨。アプリ異常終了で破損
     しない。電源断では直近トランザクションを失い得る——文書化済み)
   - **migration** (migrate.rs): `PRAGMA user_version` 管理・順方向のみ・
     1件=1トランザクション・失敗時rollback・スタートアップ冪等
     (適用済みスキップ)。**適用前backupは `VACUUM INTO`** (WAL安全。
     メインDBファイルの単純コピーは禁止事項としてdoc明記)。
     backupは読み取り専用で開き直して `PRAGMA integrity_check` で検証、
     世代保持 (既定3世代、`db-backups/library-pre-v{N}-{時刻}.sqlite3`)。
     `user_version=0` で非管理テーブルが存在するDBは「unmanaged」として
     拒否 (他アプリのDBを上書きしない)
   - **migration #1** (schema.rs): 12テーブル全部 + インデックス。
     DDLは data-model.md §2〜§12 準拠。AiProfile/AiRunはWP-10で追加
     migration予定 (`ai_run_id` 列はFKなし整数のみで確保)
   - **repository実装** (repos.rs): `SqliteRepos` が gento-core の
     `LibraryRootRepo` / `FileRepo` / `AssetRepo` を実装。WP-2が必要とする
     最小範囲 (root: add/list/set_enabled/remove/overlapping_roots、
     file: upsert (root_id+rel_pathキー) /set_scan_state/list_missing/
     find_by_path、asset: create (content_hash一意) /find_by_hash/link_file)
   - **診断** (diagnose.rs): `Db::diagnose()` が integrity_check・
     foreign_key_check・schema_version・journal_mode・12テーブル行数・
     DB/WALファイルサイズ・busy_timeout を返す
2. **`crates/gento-core/src/repo.rs` 新設** — repository traitとレコード型
   (既存コードの意味変更なし。`lib.rs` は module宣言・re-export・
   `HealthInfo.db_open` 追加のみ):
   - trait: `LibraryRootRepo` / `FileRepo` / `AssetRepo`
   - 型: `LibraryRootRecord` / `FileRecord` / `AssetRecord` /
     `FileUpsert` / `NewAsset` / `ScanState` / `TriageState` / `HashState` /
     `RepoError` (NotFound/Duplicate/Db(String)) / `path_is_within`
     (親子パス判定の雛形。WP-2で二重登録警告に使用)
3. **格納規約の確定** (PM計画§6-4):
   - UUIDv7: uuid crate (`=1.26.0`, feature `v7`)。TEXT 36文字小文字。
     **一意性のみ保証し単調性は保証しない** (ids.rs doc commentに明記)
   - 日時: DBレコードのライフサイクル時刻はUTC RFC3339 TEXT
     (`YYYY-MM-DDTHH:MM:SS.mmmZ`。chrono非依存の自前変換 — Hinnant算法)。

## DDL要点 (migration #1 = 12テーブル + 8インデックス)

- `library_roots`: uuid/path BLOB+path_encoding/display_path/enabled +
  `UNIQUE(path_encoding, path)` (パス重複検出)
- `assets`: content_hash UNIQUE + hash_algorithm CHECK('blake3') +
  hash_state + 寸法/アニメ情報 + rating 0..5 CHECK + triage CHECK +
  favorite
- `files`: root_id FK (CASCADE) + **asset_id FK (RESTRICT・NULL可)**
  (Asset作成前の走査中Fileを管理。RESTRICTによりFile残存中のAsset削除を
  拒否しメタデータ喪失を防止) + rel_path BLOB + `UNIQUE(root_id,
  path_encoding, rel_path)` + scan_state CHECK (missing≠削除の区別) +
  mtime_ms/ctime_ms/os_file_id + idx_files_asset_id/idx_files_scan_state
- `tags` (normalized_name UNIQUE) / `asset_tags` (PK(asset_id,tag_id) +
  source CHECK + idx_asset_tags_tag_id) / `captions` (kind CHECK +
  部分UNIQUE `WHERE current=1` + idx(asset_id,kind)) / `collections`
  (smart は query_json 必須CHECK) / `collection_items` (PK +
  idx(asset_id)) / `asset_metadata` (正規化列群 + seed はTEXT + raw_* JSON +
  UNIQUE(asset_id, parser_name)) / `jobs` (status+priority CHECK +
  idx_jobs_status_priority) / `file_operations` (status CHECK +
  request/result JSON) / `embeddings` (UNIQUE(asset_id, purpose,
  model_name, model_revision) + dtype CHECK)
- 全uuid列: `CHECK (length(uuid) = 36 AND uuid = lower(uuid))`

## 逸脱・判断記録

- **DB open失敗時もアプリ続行**: setup失敗で落とす代わりに
  `AppState.db=None` + warnログ。理由: 本WP時点でDBを必要とする製品機能
  は未実装 (WP-2以降) であり、DB不調でファイラーとしての起動まで妨げる
  リスクを避けた。WP-2で登録ルート機能が入る際にこの方針を再検討すること
  (DBなしでは登録機能が使えない旨のUI案内が必要になる)
- **`synchronous=NORMAL` 採用**: PM指示には未指定のため判断記録。
  WAL+NORMALはSQLite公式推奨 (アプリクラッシュで破損なし、電源断で
  直近トランザクション喪失の可能性)。画像カタログ用途に適合
- **backupの実装は `VACUUM INTO`**: 指示は「Backup API または VACUUM INTO」
  のいずれか。rusqliteのbackup featureは接続間copyの正規手段として有効化
  したが、実装はファイルへ書き出すVACUUM INTOを採用 (コードが単純・
  接続を跨がない・WAL未checkpoint分を含むことをテストで証明)
- **`crash_simulation` の `std::mem::forget`**: 接続を閉じずにリーク
  させることでプロセス死亡をシミュレート (テストプロセス内で1回のみ。
  実害なし)
- **reader接続はREAD_WRITEで開く**: 読み取り専用フラグにするとWAL
  recovery場面 (クラッシュ直後等) で書き込みが必要になり失敗し得るため
- **`hash_algorithm` CHECKは'blake3'のみ**: 将来アルゴリズム追加時は
  migrationで拡張 (追加方式方針に従う)
- api-contractの`db_status`は§16として追記 (§14 devtoolsの後に連番)

## 残リスク / 次WPへの引き継ぎ

- **WP-2**: 差分スキャンは `files` の `UNIQUE(root_id, path_encoding,
  rel_path)` + `find_by_path` + upsertで乗る。親子二重登録警告は
  `overlapping_roots` を使用 (字面比較のためcanonicalizeしてから渡す)。
  BLAKE3計算後 `find_by_hash`→`create_asset`/再利用→`link_file`。
  OSファイルIDは `os_file_id` 列 (NULL許容) へ
- **ai_run_id** (asset_tags/captions): WP-10でai_runsテーブル作成時に
  FKを付与するmigrationを追加すること (現状は整数のみ)
- **Windows非UTF-8パス**: 現状lossy UTF-8のみ (WP-17でWTF-8/UTF-16
  完全保持を再検討。`PathEncoding` にタグ追加で対応可能な設計)
- **FTS5テーブル**: migration #1には含めない (WP-8でAsset検索文書設計と
  ともに追加migrationで作成)
- **backupの世代フィールド**: `backup_generations` はDbOptionsで設定可能
  にしてあるが、UI設定は未実装 (WP-15)。現状は既定3世代固定運用
- **repoテストのTempDir**: 既存規約 (`std::env::temp_dir` + 手動掃除)
  に従いtempfile crateは未導入
- バックアップdir内の古い形式ファイル (プレフィックス不一致) は回収
  対象外 — プレフィックス `library-pre-` のファイルのみ世代管理する
