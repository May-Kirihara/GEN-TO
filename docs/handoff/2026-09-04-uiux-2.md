## A. wedge修正 (backend・最重要)

### 機構の確定 (QA reproの決定論テスト化で特定)

- `remove_root` (library.rs) は `stop_watcher` + DB行削除のみで **`cancel_scan()` を
  呼んでいなかった**。走査中に解除されても walkは処理を続ける。
- `ScanFs::walk` (PlatformFs → gento-image `scan_images` → WalkDir) には**中断経路が
  存在しない** (sinkは値を返さない・cancel引数も無い)。列挙が終わるまで
  `run_scan_all` は返らず、`scanning` フラグがtrueのまま残る。
- `scan_start` は `is_scanning()` で拒否するため「スキャンが既に進行中」が
  恒久的に出続ける。`/` 規模では列挙+処理が実質永久 = **wedge** (再起動で回復)。
  FKはON (`files.root_id → library_roots ON DELETE CASCADE`) のため解除後の
  バッチflushはFKエラーになるが、列挙自体は最後まで続く。
- **決定論redの再現方法**: `ScanFs`注入 (既存 `with_fs` 経路) の `GatedScanFs` —
  PlatformFsの列挙に挟んで「テストの解放またはcancel観測まで各エントリを
  sinkへ手放さない」ゲート。cancel観測後は残エントリを素通り (scan_rootのsinkが
  cancelで処理skipする本番の意味論の遅延付き模型)。`/`のE2E再現はコスト・危険
  のため不実施 (WP指定どおり)。
- **red証拠**: 両テストとも「walkが最初のエントリでブロック中 (entries=1)」に
  removeしても `is_scanning()` が10秒間falseにならず失敗:
  - `remove_root_during_walk_stops_scan_promptly` (controller.remove_root経由)
  - `root_row_removal_during_scan_triggers_liveness_watchdog` (DB行直接削除 =
    cancel発火なし経路)
  - 途中経過: 最初のred実行は「walkが開始しない」で失敗 — ヘルパー内ローカル
    `TestDir` がDropでデータdirを消し、walkが空で即完結していた (デバッグ_printで
    特定)。ヘルパーがTestDirを返すよう修正して本来のredに到達。

### fix設計 (二重防御) と選択根拠

1. **`remove_root` は走査中なら `cancel_scan()` を発火** (即時性)。
   `is_scanning()` ガード付き — アイドル時の解除に残置cancel (maintenance再提出
   停止の副作用) を残さない。
2. **`RootLivenessWatchdog`**: `run_scan_root` がwalk生存期間中、250ms周期で
   DBのルート行存在を照会し、消失ならcancelを立てる (頑健性 — remove_root経由
   しない行削除も捕捉)。sleepの代わりに `recv_timeout` を使い、stop送信で即時
   join (走査ごとのjoin遅延なし)。照会失敗は生存扱い (誤キャンセル防止)。
   - 選択根拠: PM案の「roots_changed世代トークン」も比較はwatchdogスレッドを
     必要とし、トークンはcontroller経路の削除しか捕まえない。DB存在照会は
     あらゆる削除経路を捕捉し同等の単純さのためこちらを採用。
   - `Shared.cancel` を `Arc<AtomicBool>` 化 (GatedScanFsが同一フラグを観測する
     ため。本番コードの挙動は従来と完全に同一)。
3. **liveness green証拠**: 両テスト0.42sで合格 (cancel→walk完結が即時)。

### 挙動の正確な記録 (PM予想との差異)

- PM予想は「multi-root走査全体が止まる」だったが、実際は**後続ルートに影響しない**:
  cancelは次の `run_scan_root` 開始時点で解除され、解除されたルート自身は
  DB行消失で再照会skipされる (予想より良い挙動。remove_rootのdoc commentに明記)。
- **既知の制限 (正直な申し送り)**: walk列挙そのもの (readdir) は traitに中断経路が
  ないため、cancel後も「処理なしの列挙tail」だけが走る (`/` で最悪数分程度)。
  完全な即時中断には gento-core `ScanFs::walk` シグネチャ変更 (crates/) が必要 =
  スコープ外のため不実装。DB書き込み・ハッシュ・FKエラーは即座に停止するため
  QAのwedge症状 (恒久scanning・再スキャン拒否・時間経過での悪化) は解消。
  **→ UIUX-3で解消**: `ScanFs::walk` がcancelを列挙境界で観察し、列挙自体が
  即時停止する (crates/gento-core + gento-image)。本節の申し送りは解決済み。

## B. 危険パス登録の確認dialog (frontend)

- 純粋関数 `needsRegistrationConfirm(path)` (library.ts): POSIX絶対depth≤1
  (`/`・`/home`等。`/home/user`は対象外)・Windowsドライブルート (`C:\`・`C:`・
  区切り/大小文字不問)・UNC共有ルート (`\\server\share`。より深い部分は対象外)。
  ブロックリスト不要の構造規則。red 5件→green。
- `ConfirmRegistrationDialog.svelte` 新規 (DeleteForeverDialog様式: backdrop +
  role=dialog + aria-modal + focusTrap + Escape取消。警告文言はWP指定文 +
  パス表示)。test 4件 (文言・パス・Cancel不発火・OK・Escape)。
- **適用箇所 = addRootを呼ぶ全入口** (grep確認で2経路):
  - FolderTree右クリック → App `registerRootFromTree` → `requestAddRoot`
  - LibraryPanelフォーム → 新prop `onAddRoot` (=App `requestAddRoot`)。
    LibraryPanelは直接 `library.addRoot` を呼ばなくなり、確認ゲートを
    構造的に通る。成功時のlibrary表示切替はApp `addRootConfirmed` が担う
    (従来UXと同一)。
- E2E (uiux1 6c): `/` 行右クリック→登録→**確認dialog表示 (xrc=1)**→
  Escape取消→**roots不変・表示遷移なし**。実際の登録は不実施 (WP指定)。
