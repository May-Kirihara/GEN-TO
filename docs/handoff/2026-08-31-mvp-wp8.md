## 既知問題「ファイル操作後のグリッド空白化」— 調査結果と修正

**根本原因 (特定・修正)**: generation変化で `GridStore.onReset` が
ready/pending地図をクリアするが、サムネイル需要スケジューラ
(`fireDemand`) は `viewportChanged` の再発火なしには実行されなかった。
スクロールも**件数変化もない**generation変化 (リネーム・同数移動後の
ライブラリスナップショット反映 — virtualizerはcount不変なので
viewportChangedを再通知しない) では需要が恒久的に再計画されず、
可視セルが空白化する (DB/FSは正しく、表示のみ。WP-7 handoff既知1と
合致する「まれに」= 件数不変ケースでのみ発生)。

**修正**: `refetchVisibleAfterReset` がページ再取得に加えて
`scheduleDemand()` を呼ぶように修正 (WP-6で入れたonReset再取得の
取りこぼし箇所)。回帰テスト
`grid-store.test.ts「WP-7既知1: generation変化のみでもサムネイル需要が再計画される」`
が再現→修正を固定する。**E2Eのリネーム先行回避の撤廃**: 上記は表示経路の
問題だったため、修正後はリネーム先行の順序でE2Eを書ける
(今回のE2Eでは検索→メタデータ編集→再実行でgeneration変化経路を通過)。

### FG-WP8: 当初3失敗 (rating / after edit / refresh) の根本原因と修正

当初の実行は 5 PASS / 3 FAIL で、旧稿は「InfoPanel詳細取得とボタンclickの
タイミング問題と推定 (ハーネス側)」と記載していた — **この推定は誤りだった**が
「ハーネス側」という方向自体は半分正しかった。調査 (WP-5コミット済みドライバ
wp5_e2e.sh と devtest.ts のキー表の突合、E2EログのM行比較) で2つの原因を特定:

1. **E2Eドライバのキー誤り (失敗の直接原因)**: 評価5クリックを
   `ctrl+shift+F5` で送っていたが、dev bridgeのキー表では
   `ctrl+shift+F5` = `focusCell1` (WP-5のctrl+shift+F2..F8着地フォーカス
   ブロック)。結果1件のグリッドで cellAt(1) はnull → `?.click()`相当の
   無音no-op となり metaRate5 が一度も発火しなかった (`asset:updated`が
   来ないのも当然)。**metaRate5 の正しいキーは `ctrl+F4`** (WP-5ドライバ
   が最初から使用)。3失敗はこの単一no-opの連鎖。ドライバを修正。
2. **実プロダクトの潜在欠陥 (キーを直えても残る問題)**: 検索表示への
   切替 (`runSearch`/`refreshSearch`/`exitSearch`) がフロントエンドの
   カタログソース状態 (`catalogSource`) を維持していなかった。一時走査
   (temp) ビューから検索すると、検索結果は全て安定AssetId (backend側は
   `CatalogMode::Library`。api-contract §42) なのに、InfoPanel編集可否・
   `asset_detail` 詳細取得効果・高速選別キーがすべて `catalogSource ===
   "library"` ゲートで無効化された (E2E step3の `M edit=0` がこの症状。
   step5bが偶然 `edit=1` だったのは、step4のコレクション表示が
   `showCollection` で catalogSource をlibraryにしていた名残)。
   **修正**: 検索3遷移で `catalogSource = "library"` を設定
   (showCollectionと同一規則)。あわせて、3箇所に重複していた編集可否規則
   (`item.dbState === "asset" && library系`) を `lib/metadata.ts
   canEditMetadata` へ集約し、回帰テスト
   `metadata.test.ts「canEditMetadata」` (5件。検索結果表示=
   library系を含む) で固定。E2E修正後のstep3は `M edit=1` を観測。

- 注意 (E2Eデータセット作成の落とし穴): 合成PNGを全ファイル同一バイトに
  するとBLAKE3内容ハッシュで6ファイルが1 Assetへ統合され、検索件数が
  「1」になる (Asset統合モデルの正しい挙動。wp8_mkdataset.pyは
  ファイルごとにユニークバイトを生成する)。

## QA-WP8 レビュー対応 (2026-09-01)

QAレビュー (Major 1件 + Minor 6件) への対応。全項目対応済み。

### Major-1: 検索系コマンドの非ブロッキング化

- `search_run` / `search_refresh` / `fts_integrity` / `fts_repair` を
  **async command化**し、DB重処理 (一致全件収集・表示レコード構築・
  索引診断/修復) を `tauri::async_runtime::spawn_blocking` へ移した
  (WP-7 `file_ops_execute`・`fts_rebuild` と同じ方式。spawn_blocking
  利用箇所: search.rs内4コマンド)。カタログロック・イベント発火は
  収集完了後の短時間のみ
- **収集上限の設定値化は見送り** (判断記録): `SearchDisplay.records`
  が全件表示の正本のため、先頭N件打ち切りはtotal/shown乖離という
  新たなUI課題を生む。async化でUIブロッキングは解消しており、
  フル収集 (上限10万件) を維持。release実測: **広域クエリ「画像」
  (5万一致) の全収集465ms** (10ページ×5000件。
  `search_performance_50k_synthetic` 拡張で常時計測)。
  measurements/wp8-search-50k.md に「実経路」節を追加
- E2E 8/8 維持 (async化の回帰なし)

### Minor対応

2. **スマートコレクション形式の統一 (v2)**: CollectionsPane条件ビルダー
   (`buildQueryJson`) が **version 2 (AST保存形式) を書き込む**ように
   変更。`CollectionsStore.createSmart` は `searchJson` 引数経由へ
   (旧`queryJson`引数は `"{}"` ダミー — SearchStore.saveと同一規則)。
   `parseQueryJson` はv2 (ビルダー表現可能なfield terms) と旧形式の
   両方を読み取り、新規 `describeQueryJson` が**任意のv2 termを概要
   表示** (「(条件表示不可)」の解消 — テキストtermは「語」、addedは
   「追加日:from〜to」等)。api-contract §42の「新規書き込みは拒否」を
   実態 (旧読み取り可・UI新規書き込みはv2・旧引数は互換で受付) へ修正
3. **スコープラベル**: 検索範囲「現在のフォルダ」→「現在のフォルダ
   （登録ルート全体）」+ selectのtitleに「サブフォルダ単位の絞り込みは
   なし」を明記 (真のサブフォルダスコープは未対応のまま設計維持)
4. **README更新**: 左ペイン (コレクション/保存済み検索) と検索バー
   (構文例込み) を実装済みの記述へ更新
5. **search_asset_idsのcountフォールバック**: offset>0空ページ時の
   count文失敗を `unwrap_or(0)` で握り潰さずエラー伝播へ
   (total=0の虚偽表示防止 — gento-db)
6. **表記**: grid-store.test.tsの「修复」中国語コメントを日本語化
7. **canEditMetadata回帰テスト**: catalogSource遷移の観点
   (libraryBacked=false時の対比アサーション) を追加し、遷移実装の
   E2E step3/5b依存をコメントで明示
