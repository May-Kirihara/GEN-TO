## 監視プロトコル (要約。api-contract §20に詳細)

監視確立 → バッファリング (400ms debounce・パス単位結合) → 初回スキャン →
キューイベント適用 (スコープ差分スキャン = reconciliation)。イベント欠落は
全体再スキャンで収束。差分スキャンはファイルシステムの最終状態のみに依存して
冪等のため「大量イベント後も最終状態一致」が成立 (実inotifyテストで証明)。

## AssetId設計 (要約。api-contract §19に詳細)

- リンク済み (ハッシュ計算済): `id = assets.id` (restart後も不変。
  同一内容の複数Fileは同一idを共有)
- 未リンク (ハッシュ待ち): `id = 2^63 | files.id` (仮ID。bit63はSQLite
  INTEGER範囲外のため assets.id と衝突しない)。ハッシュ完了で安定IDへ切替
- **WP-5のメタデータ編集は安定ID (assets.id) を使うこと** (仮IDは過渡状態)

# FG-WP2: 正確性レビュー対応 (2026-08-30)

Codexレビュー (/tmp/codex-mvp-wp2-review.md, verdict: reject) のブロッカー
6件全件と、価値が高く安価な非ブロッカー4件を修正した。

## ブロッカー修正 (全件)

### 1. 世代検証付きハッシュ/リンク
- **`gento-image/src/hash.rs`**: BLAKE3計算はopen済みfdから読む (rename/replace
  のinode差し替えの影響を受けない)。計算前後でfdメタデータ (size+mtime) を
  比較し、変化があれば `HashFileError::Stale` で結果を破棄。`FileContentHash`
  に検証済み観測 `mtime_ms` を追加。
- **`gento-core::library::hash_and_link_file`**: リンクは書き込みトランザク
  ション内で `get_file(file_id)` のDBレコード (size, mtime) と突合し、一致時
  のみ `create_or_get_asset` + `link_file` を実行。不一致は `Stale` (未リンク
  のまま次回スキャンで再ハッシュ)。**古いジョブ完了が新しいスキャンの後に
  到着しても誤リンクしない** (新しいスキャンがレコードを更新済みのため突合
  が落ちる)。プローブ (`probe_dims`) は期待メタデータを引数に取り、前後
  statで検証してズレたら寸法を破棄 (プローブとハッシュの別読み不一致対策)。
- テスト: `hash_discarded_when_generation_differs_from_record` /
  `stale_hash_job_after_newer_scan_does_not_relink` /
  `probe_bound_to_hash_metadata_drops_dims_on_mismatch` (core) +
  `stable_file_hash_carries_verified_mtime` /
  `probe_dims_bound_to_expected_metadata` (image)。
  なお「計算中のin-place変更」の実fs再現は決定的に作れないため、Stale経路
  はfakeによる検証 (実fsは安定ファイルの検証済みmtime確認まで)。

### 2. 移動検出の内容検証
- `observe()`: os_file_id一致に加え **size+mtime一致を必須化**。不一致は
  移動扱いせず新規upsert (asset引き継ぎなし) + 旧パス行はmissing化。
  missing行を無期限保持する前提でのinode再利用もsize照合で保護。
- テスト: `relocation_with_size_mismatch_is_not_a_move` /
  `relocation_with_mtime_mismatch_is_not_a_move` /
  `inode_reuse_against_missing_row_with_size_mismatch_is_not_relocation`。

### 3. 移動失敗の伝播
- `flush()`: `Duplicate`/`NotFound` は通常upsertへフォールバックし、
  旧file_idをseenから解除 (旧パス行を確実に不在化)。DB・制約エラーは
  バッチごと失敗させスキャンエラーとして伝播 (tauri層で集計・ログ)。
- テスト: `relocate_duplicate_falls_back_to_upsert_and_missing_marks_old` /
  `relocate_not_found_falls_back_to_upsert` /

### 5. pending hash会計の正確化
- **会計方式**: `hash_pending = 新規Enqueued成功数 − プール完了通知数`。
  - `enqueue_hash_jobs`: submit直前に+1、`MergedExisting` (dedup統合) は
    即座に-1 (元ジョブの完了通知1回で元の増分のみ相殺されるため)、
    `QueueFull`/`Shutdown` 拒否は-1 (放棄分は計上しない)。
  - 減算は **会計スレッド** (`spawn_hash_accountant`) がプール完了チャネル
    (Completed/Failed/Cancelled — panic隔離・shutdown放棄のCancelledも含む)
    を1通知=1減算で処理。`HashJob::run` 自身は減算しない (実行経路すべてで
    完了通知が1回来るため、run内減算は二重引き・漏れの温床だった)。
  - 終了時: workerのShutdown処理内でpool.shutdown() → 残ジョブのCancelled
    完了通知が会計スレッドに流れ、poolのArc全dropでチャネルが閉じたら
    会計スレッドも終了 → **終了時に会計は厳密に0**。
- テスト: `hash_accounting_is_exact_under_dedup_queue_saturation_and_shutdown`
  (dedup二重計上なし / capacity=2に5件で2のみ計上 / shutdown放棄も0に収束) /
  `cancelled_hash_jobs_settle_pending_to_zero` (キャンセル混在で会計0) /
  `remove_root_while_scanning_and_hashing_keeps_controller_healthy` (稼働中
  ルート削除後も会計0・controller健全)。

  しない。不完全走査は `errors` カウントと `error_samples` に警告として反映。
- テスト: `partial_walk_blocked_subtree_is_not_missing_marked` /

# FG-WP2-2: 世代トークン再設計 (2026-08-30。レビューラウンド2)

Codexレビューラウンド2 (/tmp/codex-mvp-wp2-review-2.md, verdict: reject) の
ブロッカー4件を修正した。ラウンド1は各機構を個別修正したが根因は
世代トークン (size+mtime_ms) が弱いことだったため、今回はトークン自体を
再設計し全機構をそこへ束ねた。

## トークン設計の最終形

- **型**: `gento_core::library::GenerationToken { os_file_id: Option<OsFileId>,
  byte_size: u64, mtime_ns: u64 }`。os_file_idはUnixでは (dev, ino)。
  mtime_nsは `SystemTime` のns精度観測 (取得不能環境の0詰めフォールバック
  含め同一環境内の比較として一貫)。
- **保存列**: `files.mtime_ns INTEGER NULL` (**migration #4**。schema #1凍結を
 遵守しgreenfieldでも#4で追加)。既存 `mtime_ms` 列は後方互換で残し、走査は
  両方更新 (`map_file` は `Option<u64>` で読む。NULL行=未再走査の旧行で、
  トークン照合は不一致=Staleの安全側)。os_file_id・byte_sizeは既存列。
- **照合箇所** (=トークンが流れる経路):
  1. 走査 (walkdir stat) が `ScanEntry { byte_size, mtime_ms, mtime_ns,
     os_file_id }` を観測 → upsert/relocateでfiles行へ保存
  2. `scan_root` の変化判定: トークン全体 (size/mtime_ms/mtime_ns/os_file_id
     のいずれか) が違えば upsert + asset detach。同一なら書き込みゼロ高速
     パス (ns差のみの同一ms内置換も検出= detach対象)
  3. `PendingHash { file_id, path, token }` — ハッシュジョブが走査時観測
     トークンを携帯
  4. `hash_and_probe_file` (gento-image): 開いたfdのfstatからトークン取得
     (パス再解決しない)。fdトークン ≠ expect なら**計算前にStale**。
     BLAKE3計算 → 同一fdからPNGプローブ → 計算後のfdトークン不変を検証
  5. `hash_and_link_file` (gento-core): リンクは書き込みトランザクション内で
     `token.matches_record(&row)` (= os_file_id・size・mtime_nsすべて一致、
     NULL mtime_ns行は不成立) を確認してから `create_or_get_asset` +
     `link_file`。不一致は `HashFileError::Stale` で結果破棄
- なぜ閉じるか: 同パス再利用 (新inode) はinode差でStale。同一inodeの移動は
  同一バイトなのでトークン一致で正リンク。同一ms内の置換はns差で検出。
  古いジョブの完了が新しいスキャンを追い越しても行トークンが更新済みで
  照合が落ちる。

## ブロッカー修正 (4件)

### 1. 不変世代トークン
上記設計どおり。`FileContentHash` の検証メタデータを `mtime_ns` +
`os_file_id` へ拡張 (mtime_msは後方互換で残す)。`HashedFile { content, dims }`
がハッシュ+プローブの束ね単位。
- テスト (core): `path_reuse_with_fresh_inode_and_matching_ms_makes_job_stale`
  (同パス再利用・同size・同一ms・ns近傍 → Stale) /
  `mtime_ns_difference_alone_discards_result` (ns差のみでStale) /
  `same_inode_move_links_under_new_path` (同一inode移動は正リンク) /
  既存 `stale_hash_job_after_newer_scan_does_not_relink`・
  `hash_discarded_when_generation_differs_from_record` をトークン比較へ更新。
- テスト (image): `hash_and_probe_rejects_replaced_file_with_matching_ms`
  (実fsでinode差し替え+mtime完全一致の敵対シナリオ。`File::set_modified`
  で旧mtimeを再現 — size・mtimeでは検出不能でinode差のみで検出される) /
  `expect_token_mismatch_is_stale_before_hashing` / `walk_collects_ns_precision_mtime`。

### 2. probe_dimsのfd束ね
`ScanFs` traitの `probe_dims` + `content_hash` を**単一API `hash_and_probe`**
へ統合。実装 (gento-image `hash_and_probe_file`) は1つの開いたfdから
BLAKE3 → rewind → PNG署名+IHDR (`probe_png_dimensions_at(&File)`) を読む。
パス再オープンは存在しないため置換ファイルの寸法混入は構造的に不可能。
既存 `probe_dims(path, expect)` 相当は内部でこのAPIを使う便宜ラッパとして
`gento_image::fs::probe_dims` に残した。
- テスト: `hash_and_probe_is_single_fd_bound_call` (core。1リンク=1呼び出し
  であることを通話カウンタで固定) / `hash_and_probe_returns_bound_hash_and_dims`
  ・`fd_probe_matches_path_probe` (image)。

### 3. 在不在の積極的証明
`Path::exists()` (権限/メタデータエラーでもfalse) を廃止し
`error_path_blocks_missing` で `symlink_metadata` を3分類:
`Ok(_)`=存在→blocking / `Err(NotFound)`=不在確定→non-blocking /
`Err(その他)`=判定不能→**blocking**。
- テスト: `absence_classification_three_branches` (image。存在/NotFound/
  親000ディレクトリ配下=PermissionDeniedの3分岐) + 既存の
  `walk_unreadable_subtree_blocks_missing_marking` (実chmod)・
  `vanished_paths_do_not_block_missing_marking` (core)。

### 4. 破棄/拒否ジョブの決定論リトライ
`Shared.hash_retry` (`HashRetry { queue, attempts, exhausted }`) を追加:
- **入り口**: `enqueue_hash_jobs` の `QueueFull` で拒否されたジョブ+残り全件
  をキューへ (従来は放置)。`HashJob` のStale完了時は行の現在トークンを
  読み直して再提出登録 (`requeue_after_stale`。リンク済み・不在・削除済み
  は対象外)。
- **トリガー**: (a) 会計スレッドが完了通知ごとに `resubmit_ready` —
  キュー空き (capacity−depth、マージン=min(64, capacity/4)) を見て再提出。
  (b) メンテナンス周期 (60秒) の `resubmit_unlinked_via_maintenance` —
  未リンクpresentファイル (`list_files_without_asset`) を断念済み以外
  再提出。**監視イベントがない不変ファイルもここで永続未解決にならない**。
- **上限**: Stale再試行はファイルごと8回 (`HASH_RETRY_MAX_ATTEMPTS`)。
  到達で断念し `scan_status.hash_retry_exhausted` へ露出。次のスキャン由来
  キューイング (`enqueue_hash_jobs` = 新世代トークン) でattempts/exhausted
  をリセット (リトライ経路の再提出ではリセットしない=上限が機能する)。
- **デッドロック修正の副産物**: 会計スレッドはプールを**Weak参照**でのみ
  持つ。強参照だと会計スレッド自身が完了チャネルの送信側を生存させ続け、
  recv が永久に閉じず `shutdown` のjoinでデッドロックする。
- テスト (tauri層・実DB+実fs): `queue_full_jobs_complete_via_completion_driven_retry`
  (capacity=4+遅延注入で確実に満杯 → 完了駆動のみで全20件リンク。イベント・
  再スキャンなし) / `stale_discarded_job_is_resubmitted_without_rescan`
  (1回目Stale→再提出→リンク。walk呼び出しは初回スキャンの1回のみ) /
  `stale_retry_attempt_cap_is_exposed_and_scan_rearms` (上限到達の露出・
  断念後の再提出停止・再スキャンでのリセット+解決) /
  `maintenance_resolves_immutable_unlinked_file_without_watch_events`
  (事前シード行+watcher確立・イベントなし → メンテナンス再提出のみで解決。
  walk呼び出しゼロ)。
