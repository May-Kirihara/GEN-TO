## 監視プロトコル (要約。api-contract §20に詳細)

監視確立 → バッファリング (400ms debounce・パス単位結合) → 初回スキャン →
キューイベント適用 (スコープ差分スキャン = reconciliation)。イベント欠落は
全体再スキャンで収束。差分スキャンはファイルシステムの最終状態のみに依存して
冪等のため「大量イベント後も最終状態一致」が成立 (実inotifyテストで証明)。

## AssetId設計 (要約。api-contract §19に詳細)

- リンク済み (ハッシュ計算済): `id = assets.id` (restart後も不変。
  同一内容の複数Fileは同一idを共有)
- 未リンク (ハッシュ待ち): `id = 2^63 | files.id` (仮ID。bit63はSQLite
  INTEGER範囲外のため assets.id と衝突しない)。ハッシュ完了で安定IDへ切替
- **WP-5のメタデータ編集は安定ID (assets.id) を使うこと** (仮IDは過渡状態)

## 主要判断・逸脱

| # | 判断 | 理由 |
|---|---|---|
| 1 | ライブラリカタログのページ取得は「DB→スナップショット一括生成→既存ページAPI」の2段構成 (SQL直接ページングでない) | generation/protocol/thumbnail機構 (メモリ上レコード解決) をそのまま再利用。5万件メモリ保持はスパイクの仮想カタログで実績済み。直接SQLページングはWP-4 (3ペインUI) で発展させる |
| 2 | 変更検出時 (size/mtime変化) はassetリンクを一度NULL化し再ハッシュで再リンク | 列追加不要 (migration #2をindexのみに保つ要件)。同一内容なら同一Assetへ再リンクされメタデータは失われない (`changed_file_upserts_and_detaches_asset` で検証) |
| 3 | `scan:progress` を一時走査とライブラリで共用 (フィールド追加: updated/relocated/missing/hashed/pending_hash/phase) | UI進捆表示が単一リスナーで済む。追加フィールドは後方互換 |
| 4 | ハッシュはサムネイルとは別の専用プール (2ワーカー・Background) | `WorkerPool` の優先度/キャンセル/pause機構を再利用しつつ、Interactive/Viewportのサムネイル生成をハッシュが飢餓させない分離 |
| 5 | 親子二重登録は警告 (`overlapping` フィールド) であって拒否しない | spec-draft §4.2が「警告または登録制限」を選択可能のため |
| 6 | 変化なsdiffスキャンは書き込みゼロ (last_seen_atも更新しない) | 5万件規模で毎回全行UPDATEを避ける。WP-1の規約「存在確認の反映はupsert (発見) のみ」と整合 |
| 7 | `set_catalog_mode` (devtools) はLibrary表示中エラー (`"switch to temp source..."`) | real↔virtualは一時走査カタログ上の操作という従来意味を保持 |
| 8 | watcherのルート不在検出は「watcher停止+roots:changed+DB保持」。ルート自体の再関連付け (改名/再マウント/大文字小文字) は将来課題 (冒頭のCodex指摘どおりMVP外) | |
| 9 | スキャン中にUIページ取得: スナップショット反映はスキャン位相の合間 (ルート単位) + ハッシュは100ms間隔 | 書き込みは既に小バッチ化+WAL reader分離でブロックなし (テスト `reader_queries_stay_responsive_during_batch_writes`) |
| 10 | notify 8.2.0 (9.0.0系はrcのため) / blake3 1.8.7 | dependency-notes.mdにlicense・推移依存を記録 (inotifyはISCと判明——初回記載のMITから訂正済み) |

## 受け入れ条件 → 検証の対応 (§10)

1. **再起動後も登録ルートと一覧が復元** —
   `restart_restores_roots_files_and_links` (gento-db。Db reopenで
   roots/files/assetリンク完全復元) + `add_scan_hash_and_restart_restore`
   (tauri。コントローラ再作成で同一AssetIdのスナップショット復元)
2. **追加・変更・改名・移動・削除をDBへ反映** —
   `watcher_converges_on_external_changes` (実inotify: 新規/変更/
   rename (inode保持でrelocate)/削除 (missing化) の収束をポーリング検証) +
   core単体テスト (fake fs: `changed_file_upserts_and_detaches_asset` /
   `moved_file_rediscovered_by_os_file_id_keeps_identity` /
   `removed_file_becomes_missing_not_deleted` など)
3. **同一バイト内容の複数ファイルが1 Assetを共有** —
   `hash_and_link_shares_asset_between_identical_files` (core) +
   `add_scan_hash_and_restart_restore` (tauri。同一AssetId検証) +
   **実リリースバイナリE2E**: sample/dataset 1615ファイル → 974 Asset
   (同一内容統合を実物で確認)
4. **不在ファイルのメタデータを即時削除しない** —
   `removed_file_becomes_missing_not_deleted` (missing化でもレコード・
   uuid保持) + `remove_root_deletes_files_but_keeps_assets` (root解除時も
   Assetは保持)
5. **大量監視イベント後も最終状態一致** —
   `watcher_burst_of_many_events_converges` (60ファイル作成+20削除の
   バースト → present=41/missing=0 に収束)
6. **初回スキャン中も既存一覧を操作できる** —
   `reader_queries_stay_responsive_during_batch_writes` (1000ファイルの
   10バッチ書き込み中、readerのページングクエリが全成功) +
   スナップショット反映はスキャン位相の合間 (一覧は常に旧世代を返し
   staleGenerationでのみ再取得)
7. **テスト基準** — cargo **290 passed** (基準243超。core 53 / gento-db 75 /
   image 84 / tauri 78)、vitest **234 passed** (基準221超)、
   `cargo fmt` / `cargo clippy -D warnings` (通常+devtools) /
   `cargo check --release` (featureなし・custom-protocol,devtools) /
   `pnpm check` (0 errors / 7 warnings 既存) / `pnpm test` / `pnpm lint` /
   `pnpm build` すべてクリーン
8. **`sample/dataset` 読み取り専限・テスト非依存** — 自動テストはtempdir
   のみ。実アプリスモークはsample/datasetを /tmp へコピーして使用
   (sample自体は無変更)

## 残リスク /次WPへの引き継ぎ

- **GUI操作の自動化は未実施**: UIボタン経由の追加/解除/切替は手動確認
  (コマンド層はcontrollerメソッドのthin wrapperで、controllerは実DB+実
  inotifyでテスト済み)。WP-4 (製品UIシェル) でE2Eを整備する際にカバー
- **ルート自体の再関連付け** (改名/再マウント/大文字小文字の同一判定) は
  MVP外 (Codex指摘のとおり)。不在ルートは無効表示+DB保持のみ。将来は
  ルートUUIDベースの再関連付けを検討
- **`scan_stop` はキューを残す**: 現在実行中のスキャンのみキャンセル。
  監視イベント由来のスコープ差分は停止後も適用され続ける (設計どおり)。
  「完全停止」が必要になった場合はキュードレインを追加
- **ハッシュ QueueFull 時の残件**: 次回スキャンのresumeに任せる設計
  (8192件キュー上限。5万件初回でも到達しない想定だが、超過時は
  `pending_hash` が残る)
- **observerのinotify上限**: ユーザーのinotify watch上限
  (`fs.inotify.max_user_watches`) を超える大規模ツリーではwatcher追加が
  失敗し得る (warnログで継続。スキャン自体は影響なし)。WP-16の実環境
  ゲートで扱う
- **跨ルート移動**: os_file_id照合は同一ルート内のみ。他ルートへの移動は
  旧ルートでmissing化+新ルートで新規扱い (Assetはハッシュ一致で統合される
  ため実害はメタデータ重複なし。将来の改善候補)
- **`list_present_joined` は全件一括読み込み**: 5万件規模は問題なし
  (スパイク実績)。それ超過はWP-4のSQLページング化で解消
- WP-3: 形式別probe/decode (`probe_dims` のPNG以外対応)、Assetの
  width/height/mime の正本化、thumb_stateの実状態反映
- WP-5: メタデータ編集は**安定AssetId (assets.id) を使用** (api-contract
  §19)。`assets` 行のrating/triage/favoriteはWP-2で読み出しのみ実装済み
