## 監視プロトコル (要約。api-contract §20に詳細)

監視確立 → バッファリング (400ms debounce・パス単位結合) → 初回スキャン →
キューイベント適用 (スコープ差分スキャン = reconciliation)。イベント欠落は
全体再スキャンで収束。差分スキャンはファイルシステムの最終状態のみに依存して
冪等のため「大量イベント後も最終状態一致」が成立 (実inotifyテストで証明)。

## AssetId設計 (要約。api-contract §19に詳細)

- リンク済み (ハッシュ計算済): `id = assets.id` (restart後も不変。
  同一内容の複数Fileは同一idを共有)
- 未リンク (ハッシュ待ち): `id = 2^63 | files.id` (仮ID。bit63はSQLite
  INTEGER範囲外のため assets.id と衝突しない)。ハッシュ完了で安定IDへ切替
- **WP-5のメタデータ編集は安定ID (assets.id) を使うこと** (仮IDは過渡状態)

# FG-WP2: 正確性レビュー対応 (2026-08-30)

Codexレビュー (/tmp/codex-mvp-wp2-review.md, verdict: reject) のブロッカー
6件全件と、価値が高く安価な非ブロッカー4件を修正した。

## ブロッカー修正 (全件)

### 1. 世代検証付きハッシュ/リンク
- **`gento-image/src/hash.rs`**: BLAKE3計算はopen済みfdから読む (rename/replace
  のinode差し替えの影響を受けない)。計算前後でfdメタデータ (size+mtime) を
  比較し、変化があれば `HashFileError::Stale` で結果を破棄。`FileContentHash`
  に検証済み観測 `mtime_ms` を追加。
- **`gento-core::library::hash_and_link_file`**: リンクは書き込みトランザク
  ション内で `get_file(file_id)` のDBレコード (size, mtime) と突合し、一致時
  のみ `create_or_get_asset` + `link_file` を実行。不一致は `Stale` (未リンク
  のまま次回スキャンで再ハッシュ)。**古いジョブ完了が新しいスキャンの後に
  到着しても誤リンクしない** (新しいスキャンがレコードを更新済みのため突合
  が落ちる)。プローブ (`probe_dims`) は期待メタデータを引数に取り、前後
  statで検証してズレたら寸法を破棄 (プローブとハッシュの別読み不一致対策)。
- テスト: `hash_discarded_when_generation_differs_from_record` /
  `stale_hash_job_after_newer_scan_does_not_relink` /
  `probe_bound_to_hash_metadata_drops_dims_on_mismatch` (core) +
  `stable_file_hash_carries_verified_mtime` /
  `probe_dims_bound_to_expected_metadata` (image)。
  なお「計算中のin-place変更」の実fs再現は決定的に作れないため、Stale経路
  はfakeによる検証 (実fsは安定ファイルの検証済みmtime確認まで)。

### 2. 移動検出の内容検証
- `observe()`: os_file_id一致に加え **size+mtime一致を必須化**。不一致は
  移動扱いせず新規upsert (asset引き継ぎなし) + 旧パス行はmissing化。
  missing行を無期限保持する前提でのinode再利用もsize照合で保護。
- テスト: `relocation_with_size_mismatch_is_not_a_move` /
  `relocation_with_mtime_mismatch_is_not_a_move` /
  `inode_reuse_against_missing_row_with_size_mismatch_is_not_relocation`。

### 3. 移動失敗の伝播
- `flush()`: `Duplicate`/`NotFound` は通常upsertへフォールバックし、
  旧file_idをseenから解除 (旧パス行を確実に不在化)。DB・制約エラーは
  バッチごと失敗させスキャンエラーとして伝播 (tauri層で集計・ログ)。
- テスト: `relocate_duplicate_falls_back_to_upsert_and_missing_marks_old` /
  `relocate_not_found_falls_back_to_upsert` /
  `relocate_db_error_fails_scan` (競合注入はwalk開始時にreposを書き換える
  `RiggedFs` で実現)。

### 4. overflow収束の修正
- debounceループのgateを修正: `last_event == None` でも `buffer.is_overflow()`
  なら待ちを突破してdrain → 全体再スキャン。**通常イベントが1件も来なくても
  50ms tickで検出される** (overflowフラグはwatcherコールバックのエラー・
  未知イベント種経路でも立つ)。
- テスト: `overflow_without_normal_events_schedules_full_rescan`
  (debouncer単体: overflowのみ投入 → ScanRootコマンド到達を検証)。

### 5. pending hash会計の正確化
- **会計方式**: `hash_pending = 新規Enqueued成功数 − プール完了通知数`。
  - `enqueue_hash_jobs`: submit直前に+1、`MergedExisting` (dedup統合) は
    即座に-1 (元ジョブの完了通知1回で元の増分のみ相殺されるため)、
    `QueueFull`/`Shutdown` 拒否は-1 (放棄分は計上しない)。
  - 減算は **会計スレッド** (`spawn_hash_accountant`) がプール完了チャネル
    (Completed/Failed/Cancelled — panic隔離・shutdown放棄のCancelledも含む)
    を1通知=1減算で処理。`HashJob::run` 自身は減算しない (実行経路すべてで
    完了通知が1回来るため、run内減算は二重引き・漏れの温床だった)。
  - 終了時: workerのShutdown処理内でpool.shutdown() → 残ジョブのCancelled
    完了通知が会計スレッドに流れ、poolのArc全dropでチャネルが閉じたら
    会計スレッドも終了 → **終了時に会計は厳密に0**。
- テスト: `hash_accounting_is_exact_under_dedup_queue_saturation_and_shutdown`
  (dedup二重計上なし / capacity=2に5件で2のみ計上 / shutdown放棄も0に収束) /
  `cancelled_hash_jobs_settle_pending_to_zero` (キャンセル混在で会計0) /
  `remove_root_while_scanning_and_hashing_keeps_controller_healthy` (稼働中
  ルート削除後も会計0・controller健全)。

### 6. 不完全走査の保守的reconciliation
- `WalkOutcome.errors` を構造化 (`WalkError { rel_path, reason, blocks_missing }`)。
  fs実装は「パスが存在するが読めない」(権限等) のみ `blocks_missing=true`
  (「パス自体が消えた」は実際の不在のためブロックしない)。`mark_missing` は
  blocks_missingパス配下 (ルート自体の失敗=空パスなら全レコード) をmissing化
  しない。不完全走査は `errors` カウントと `error_samples` に警告として反映。
- テスト: `partial_walk_blocked_subtree_is_not_missing_marked` /
  `vanished_paths_do_not_block_missing_marking` /
  `root_level_walk_error_blocks_all_missing_marking` (core) +
  `walk_unreadable_subtree_blocks_missing_marking` (image, 実chmod) +
  `permission_denied_subtree_is_not_missing_marked` (tauri, 実chmod・復帰も検証)。

## 非ブロッカー対応

7. **migration #3** (indexのみ。列追加なし): `idx_files_root_os_file_id
   (root_id, os_file_id) WHERE os_file_id IS NOT NULL`。reconciliationの移動
   検出照合 (`find_by_os_file_id`) は「同一ルート内」条件付きのため複合index
   が実査形に適合 (旧グローバルindexは後方互換で残す)。`LATEST_VERSION=3`、
   v2保持DBからの移行はbackup作成後に適用
   (`v2_database_upgrades_to_v3_with_backup`)。
8. **orphan Asset保持の明記**: api-contract §17 `library_roots_remove` に
   「設計上の保持」(同一内容再発見時の統合・メタデータ保護) とWP-15でのGC
   検討を明記。
9. **ルート不在化でdebouncerがexitしてwatcherが残る問題を修正**: ルート
   削除 (アンマウント含む) を検出したdebouncerは自己登録解除してwatcherを
   解放 (inotify返却)。メンテナンス周期 (60秒) でルート再出現を検出し
   watcher再確立+再スキャン
   (`maintenance_reestablishes_watcher_after_root_reappears`)。
10. **watcher確立失敗の劣化運用**: `scan_status.watch_degraded` フラグを
    暴露 (有効・監視ON・パス存在なのにwatcher無し)。メンテナンス周期で
    再確立を試行し、失敗する間は60秒毎のポーリング再スキャンで変更を拾う
    (`maintenance_degraded_polling_rescans_when_watcher_unavailable` /
    `watch_degraded_reflected_in_scan_status`)。メンテナンスは新規スレッド
    なし (ワーカーループの `recv_timeout` アイドルで実行)。
