## AVIFの成否と詳細 (blocked-avif)

- 試行: workspace `image` featureへ `avif-native` を追加し `cargo check -p gento-image`
- 結果: **失敗** — `dav1d-sys` がシステムライブラリ `dav1d` をpkg-configで
  要求するが本環境に存在しない:
  `Package dav1d was not found in the pkg-config search path.`
  (`pkg-config --exists dav1d` も失敗を確認済み)
- 対応: featureを戻して6形式で完成。**代替経路は発明していない**
- コード側はAVIFを前方対応済み: magic判定 (`ftyp`ブランド avif/avis/mif1+互換) と
  `ProbedFormat::Avif`/mime (`image/avif`) を用意し、avif-native不在時は
  probeが `Unsupported` を返す (グリッドは「未対応」表示。corruptと区別)。
  dav1d導入後にfeatureを1行追加すればprobe/decodeが有効化される
- PMアクション: dav1d (+ libdav1dの開発パッケージ) の入手調整

## 設計判断・逸脱の記録

| # | 判断 | 理由 |
|---|---|---|
| 1 | **Orientationの適用位置**: サムネイル/previewのdecode直後 (メモリ上)。ビューアのoriginal表示はWebKitのEXIF自動解釈に委ねる | キャッシュに一度適用すれば全UIで一貫。originalのバイト列は不変 (元画像非変更の阻止条件)。WebKitはEXIF Orientationを`<img>`で自動適用するため、バイトを改変せず表示向きが一致する。他WebView (WebView2/WKWebView) も同挙動だがWP-17で再検証予定 |
| 2 | **Limits値**: 既存の寸法20000 / alloc 256MiBを全形式へ適用。probeはalloc 1MiB+同寸法上限 | スパイク実績値の踏襲 (dataset最大7.9MP)。JPEG/BMPのbombは `ImageReader::decode` の total_bytes予約検査で遮断、BMP/WebPの寸法詐称はprobe側の明示検査で遮断 (各crateのset_limitsが寸法を見ないため) |
| 3 | **animated扱い**: `is_animated` = GIFは frame_count>1、WebPはANIMチャンク存在 | 1フレームGIFは実質静止画。WebPはANMF 1個でもANIMがあればanimated (再生メタデータを持つ) |
| 4 | **GIFフレーム数走査**: 自前バイト走査 (32MiB予算)。WebPはRIFFチャンクヘッダ走査 | image crateに軽量なframe_count APIが無い。フルデコードせずIOのみ。予算打ち切り時は下限値 (十分実用) |
| 5 | **ProbedFormat を gento-coreへ配置** (image crate非依存の値オブジェクト) | `HashedFile`/`ScanFs` 契約 (api-contract §20) を崩さずfd束ねを維持するため。image crateの型との対応表はgento-image `format.rs` が持つ |
| 6 | **PNGのprobeのみpng crate直読み** (IHDR読み取り) | image crateのPngDecoderはIDAT不在で構築失敗する。旧probe (probe.rs) の挙動 (IHDR+IENDのみで寸法取得) を維持し、magic詐称時の挙動互換を保つ |
| 7 | **assets列の充填**: schema #1の既存列 (`mime_type/has_alpha/is_animated/frame_count`) を使用。**migration #5は不要だった** (凍結維持) | 不足列が無かったため |
| 8 | **ALGORITHM_VERSION 1→2**: Orientation適用+全形式化でキャッシュ無効化 | api-contract §10/§22参照 |
| 9 |kamadak-exif 0.5.5 (BSD-2-Clause) を追加。変換は image crateの `Orientation::from_exif`+`apply_orientation` に一任 | 読み取りはWP-9 (EXIF全解析) でも再利用。変換の意味論実装を重複させない (1〜8全系を幾何導出の合成画像テストで検証) |
| 10 | 一時走査 (`start_scan`) を `scan_images_batch` (7形式列挙) へ切换 | E2E受け入れ「各形式1枚以上のtempdirで一覧→ビューア→サムネイル」。`scan_pngs` はAPI維持 (既存テストが依存) |
| 11 | 空ファイル・magic切り詰めは `Corrupt`、未知magicは `Unsupported` (旧PNGプローブの空ファイル=Corrupt挙動を踏襲) | 破損と未対応を区別し、グリッド表示を分ける |

## 安全性 (受け入れ条件2)

- 全形式デコードに `image::Limits` (寸法20000 / alloc 256MiB) を適用。
  テスト: PNG 100000x100000 / BMP 100000x100000 / JPEG 65500x65500 の
  寸法詐称ヘッダが拒否されること、probe段階でも寸法上限で `Corrupt`
- 変異fuzz相当: 固定シードLCGで6形式のseedを反転/切り詰め →
  probe・decode・generate が**panicしない**ことを検証
  (`format::tests::random_mutations_never_panic` /
  `thumbnail::tests::mutated_inputs_never_panic_decode`)
- fd束ね契約 (api-contract §20) は維持: プローブ形式拡張後も
  「expect一致・計算前後のトークン不変・同一fd」を全テストで維持
