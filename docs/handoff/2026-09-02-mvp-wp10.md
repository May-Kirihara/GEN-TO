   WP-9はmigrationを追加しなかった (asset_metadataは#1から存在) ため

   内容は指示どおり (ai_profiles/ai_runs/ai_run_id列/jobs本格化)。
2. **workerをtauri async runtimeでなくstd::thread**: library.rsのワーカー
   規約 (ハッシュ会計スレッド等) との一貫性と、cargo test単体テストから
   `run_one_job` を決定的にドライブできる試験性を優先した。起床条件
   (エンキュー時・resume時・500msポーリング) は指示どおり。reqwestは
   `blocking` featureを使用 (専用スレッド内のためasync runtimeを塞がない)。
3. **mock OpenAIサーバーをpython http.serverでなくin-process Rust実装**
   (`gento_ai::testserver`): 外部プロセス依存が消えCIで決定的。
   Bearer検証・遅延注入・500注入・`response_format`非対応模倣を実装済みで、
   要求されたE2E観測点をすべてカバーする。debug/devtoolsビルドのみ
   コンパイル (WP-0規約。release-smokeで隔離確認済み)。
4. **ai_profilesに`enabled`列を追加** (data-model §8.1の属性に無い):
   「有効プロファイル」(自動処理の投入先) の選択に必要なため。
   api-contract §44に記録。
5. jobs表のjob_typeにCHECK (`ai_caption_tags`/`ai_reparse`) を付与:
   将来種別 (embedding=WP-11) は既存規約どおり追加migrationで拡張する。

## APIキー保管の実装方式 (PM指示項目)

- 第一: `keyring` =4.2.0 (feature `v1` 既定 = Linux: zbus Secret Service /
  macOS: Keychain / Windows: Credential Manager。zbus 5.19.0はtauri経由で
  Cargo.lockに既存在存)。
- フォールバック: keyring保存失敗 (D-Bus不在等) 時、
  `{app_data_dir}/ai-secrets/<profile-uuid>.key` へ平文保存 (0600 +
  `_README.txt`警告同梱)。**簡易難読化は意図的にしない** — 暗号鍵を同一
  マシンに置く疑似安全を避け、平文であることを警告で明示 (PM指示どおり)。
- `ai_profiles.api_key_ref` は参照文字列 (`keyring:<uuid>` / `file:<uuid>`)。
- 実行環境確認結果: **本開発環境 (ヘッドレスLinux) にSecret Serviceは
  存在せず、保存は常にfileフォールバックになる**
  (`keyring_save_attempts_and_reports_fallback` テストは両環境で通るよう
  書いている。実機GUI環境ではkeyringが選ばれる)。
- 保護措置: `ApiKey` newtypeのDebug/Displayは `****`。鍵が出るのは
  Authorizationヘッダ構築 (`bearer_auth`) の1箇所のみ。
- 検証テスト: DB/WAL全バイト走査で鍵平文不在
  (`e2e_api_key_sent_as_bearer_and_never_in_db`,
  `save_profile_stores_key_ref_not_secret_in_dto_or_logs` — 後者は
  tracingバッファリングでログ混入も検査)。

## ジョブ状態機御の概要

状態: `queued / running / succeeded / failed / cancelled / retry_waiting`。
- claimはトランザクション内SELECT→UPDATE (複数ワーカー安全)。
  `claim_job_by_id` (飽和考慮した選択後) と `claim_next_job` (単純) を用意。
- 失敗時: attempts < max (既定3) → `retry_waiting` + `scheduled_at`=バックオフ
  期限。接続失敗と5xxのみ再試行 (4xx・パース失敗は確定failed)。
- バックオフ: `gento_core::jobs::backoff_delay_ms` — 30s→2m→8m (×4)、
  ジッター[0.5,1.5)倍、上限1h (純粋関数、単体テストで全列検証)。
- 起動回復: `recover_running_jobs` が running→queued へ (クラッシュ・
  クリーンシャットダウン両方。attempts据え置き)。
- pending中の同一 (job_type, target_id) 重複投入は部分UNIQUE indexで拒否
  (自動処理の多重エンキュー抑止)。
- キュー一時停止はメモリフラグ (永続化しない。再起動で実行再開が既定)。
