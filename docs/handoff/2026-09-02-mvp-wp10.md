## ジョブ状態機御の概要

状態: `queued / running / succeeded / failed / cancelled / retry_waiting`。
- claimはトランザクション内SELECT→UPDATE (複数ワーカー安全)。
  `claim_job_by_id` (飽和考慮した選択後) と `claim_next_job` (単純) を用意。
- 失敗時: attempts < max (既定3) → `retry_waiting` + `scheduled_at`=バックオフ
  期限。接続失敗と5xxのみ再試行 (4xx・パース失敗は確定failed)。
- バックオフ: `gento_core::jobs::backoff_delay_ms` — 30s→2m→8m (×4)、
  ジッター[0.5,1.5)倍、上限1h (純粋関数、単体テストで全列検証)。
- 起動回復: `recover_running_jobs` が running→queued へ (クラッシュ・
  クリーンシャットダウン両方。attempts据え置き)。
- pending中の同一 (job_type, target_id) 重複投入は部分UNIQUE indexで拒否
  (自動処理の多重エンキュー抑止)。
- キュー一時停止はメモリフラグ (永続化しない。再起動で実行再開が既定)。

## ブロッカー対応 (5件)

### 1. 送信画像サイズの強制上限 (64〜2048)

3層防御で原寸の外部送信経路を構造的に排除:

| 経路 | 挙動 | 実装 |
|---|---|---|
| IPC保存 (`ai_profile_save`) | 範囲外は**拒否** (日本語エラー「送信画像の最大辺は64〜2048pxの範囲で指定してください (送信は最大2048pxまで)」) | `apps/desktop/src-tauri/src/ai.rs` `save_profile_impl` |
| 保存済み値の読み込み | **クランプ** (0→64・2048超→2048。旧「0=縮小なし」プロファイルの残留値を安全側へ) | `gento-ai/src/prompt.rs` `ProfileExtra::parse` |
| 実行時 | **クランプ** (`encode_for_send` の引数を最終強制。override経路も含む) | `gento-ai/src/imaging.rs` `clamp_image_edge` |

既定1024維持 (`ProfileExtra::default`)。UI (AiPanel) は入力を
`min=64 max=2048` に変更しラベルに「送信は最大2048pxまで」を明記。

テスト: `ipc_rejects_out_of_range_max_image_edge` (0/63/2049/8192/u32::MAX
拒否・64/1024/2048受理) / `legacy_saved_out_of_range_edge_is_clamped_in_dto`
(保存値0/8192の読み込みクランプ) / `max_edge_out_of_range_is_clamped_never_full_resolution`
(実行時0→64・8192→2048) / `e2e_saved_out_of_range_edge_is_enforced_at_execution`
(8192設定プロファイルの実送信が2048へ強制)。

### 2. 非リトライ性失敗の分類 (エラー分類の最終形)

```text
retryable  = network (接続失敗/DNS/timeout)・HTTP 5xx
             → fail_job (backoff 30s→2m→8m×4 + jitter, 上限1h) → retry_waiting
permanent  = HTTP 4xx (認証・不正リクエスト)・パース失敗・プロンプト過大・
             応答過大 (2MiB超)・鍵取得失敗・プロファイル未解決・適用エラー
             → fail_job_permanent → 即座にterminal failed
               (retry_waitingに入れない・再送しない = 画像再開示の反復を構造的に防止)
```

- 分類の正本は `gento_ai::client::AiError::is_retryable` (Connect=true /
  Api>=500=true / Parse=false / Oversized=false) と pipeline/workerの
  `retryable` フラグ。repo側の新API: `gento-db jobs.rs fail_job_permanent`
  (running以外への適用はConstraint拒否・attemptsはclaim分のみ記録)。
- 旧挙動 (permanentも`fail_job`でdelay=0のretry_waitingに入り即時再送が
  attempts上限まで反復) を廃止。

テスト: `permanent_fail_terminates_immediately_regardless_of_attempts`
(gento-db) / `service_permanent_4xx_fails_once_without_retry` (401→1回で
failed・attempts==1・2秒後もchat_calls==1・retry_waiting不遷移) /
`service_5xx_goes_to_retry_waiting_with_backoff` (500→retry_waiting+
scheduled_at) / `e2e_http_401_is_permanent_and_500_is_retryable`。

### 3. プロファイル同時実行の原子化

容量チェック・claim・スロット予約を**同一の in_flight ロック内**で実行
(`run_one_job`)。旧実装は「チェック(ロック内)→予約(claim後の再ロック)」の
間に別workerが同プロファイルのジョブをclaimでき、concurrency=1でも
同時実行が成立し得た。ロック順序は常に in_flight → db で統一
(db→in_flightの経路は存在しないためデッドロック無し)。

テスト: `concurrency_one_is_enforced_across_two_workers` —
concurrency=1プロファイル+400ms遅延注入mock+2ワーカースレッド同時
ドライブ。mockに同時処理数ゲージ (`RequestLog.concurrent_max`) を追加し、
最大同時処理数==1 (直列化) と両ジョブ成功を**決定的に**検証する
(racyな時間計測でなく観測値で判定)。

### 4. HTTP応答の境界とリダイレクト

- 応答ボディ読み取りに**2 MiB上限**: Content-Length検査 (ヘッダ段階で
  即拒否) + `take(limit+1)` のストリーミング読み取り上限 (chunked応答も
  上限到達でエラー)。超過は新error種別 `AiError::Oversized` (非リトライ)。
- redirect policyを明示的に**none** (`reqwest::redirect::Policy::none()`) —
  3xxはそのまま `Api{status}` エラー。フォールバックの`Client::new()`は
  redirect既定値を復活させるため廃止しbuild失敗はpanic明示
  (Client::new()自体が失敗時panicのため旧フォールバックは実質機能して
  いなかった)。
- mock (`gento-ai/src/testserver.rs`) に `HugeBodyMode`
  (ContentLength/Chunkedの3MiB応答) と `redirect_to` (302+Location) を追加。

テスト: `client_rejects_huge_response_with_content_length` (即時拒否・
models応答は通常どおり=障害隔離) /
`client_rejects_huge_chunked_response_via_streaming_cap` /
`client_does_not_follow_redirects` (302をApi errorで返し転送先の
chat_calls==0)。

### 5. 鍵取得失敗はフェイルクローズ

プロファイルに `api_key_ref` があるのに `SecretStore::load` が失敗した場合
(keyring/fileエラー・ファイル消失)、**送信前に**ジョブをpermanent失敗
(「資格情報の取得に失敗しました (プロファイルのAPIキーが読み取れません。
保存し直してください)」)。未認証での画像送信は行わない。4種テスト機能
(`ai_profile_test_*`) も同じくフェイルクローズ (日本語エラー)。

テスト: `key_lookup_failure_fails_closed_without_sending` — Bearer検証mock
相手に鍵ファイルを消失させ、ジョブfailed (attempts==1)・**chat_calls==0・
unauthorized==0** (リクエスト自体が届かないこと) を検証。
