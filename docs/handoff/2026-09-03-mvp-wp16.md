## F3: 50kハッシュ初段低速帯 → 診断完了 (構造的・申し送り維持)

ドライバ `wp16_f3_hashdiag.py` を新設し8k/50kを再計測:

- **8kでは低速帯不再現** (19.1s/約416件/s)。**50kでは4/4再現** (旧実績込み。
  修正前再走: ~6件/s×~9分→回復し計1,197s・WAL 225.61MB凍結・CPU 250%・
  書込増幅200KB/件。fts修正後クリーン再走: fts repair **0回**・低速帯が
  **40分の計測上限まで~5件/sで持続 (回復なし)**・WAL ~236MB凍結)。
- **サムネIL競合を否定** (低速帯中 gen=30/q=0 不変)。
- **fts repair嵐 (3,300+回) の原因を特定・修正**: `fts_counts` の2COUNTが
  別snapshotで走りwriter commitを跨ぐと偽不整合 → ハッシュ中ほぼ全
  snapshot変更でwriter上の `fts_repair` が走っていた。単一SELECT化
  (snapshot一貫) で修正、回帰テスト付き (red→green)。**嵐は100%消滅したが
  低速帯自体は持続・むしろ長期化** → 嵐は症状であり原因でないことが確定
  (WAL凍結後も低速が続く走があるためWALサイズも直接因子でない)。
- **低速帯の実体**: ハッシュワーカーが各100% CPU (IO/ロック待ちでない)。
  (a) 1ハッシュemit (最大10/s) ごとに `build_library_snapshot`
  (50k行JOIN実測**76ms**) + fts_counts (14ms) + カタログ置換が**ワーカー上で
  同期実行**される O(N) 構造 (2ワーカー×emitサイクルで~5-8件/sと定量的に
  整合)、(b) 持続的writer+reader負荷下での索引書込増幅 (~200KB/件) と
  WAL checkpoint飢餓 (WAL ~230MBへ増大) の複合。速度回復の有無・タイミング
  は走により不定 (回復する走と40分回復しない走がある) — フィードバック
  dominantの性能現象。
- **判断**: emitのワーカーからの分離・スナップショット増分化・
  `ensure_fts_after_scan` の走査完了時限定起動など構造変更が必要で
  設定/順序の小修正では解消しない → **申し送り維持 (文書化のみ)**。
  fts_counts修正は独立の実欠陥として実施 (50k投入でwriter上の無駄
  トランザクション3,300+回を除去)。

## FG-WP16-4: マイルストーンr2 reject残3件 (最終ラウンド)

### 設計核心: feederのpop→投入をbacklogロックで完結

backlog feeder (`drain_backlog`) の各item処理を**backlogロックで守られた
2区間**に構造化した:

- **pop区間**: itemをdequeから `inflight` (pop_id・cancel照合用key・世代)
  へ移す。この直後から投入までの間、cancelに可視。
- **投入区間**: ①cancelがinflightを破棄していないか (pop_id一致検査)
  ②世代が現行か (`backlog.generation == item.generation`) を検査してから
  `enqueue_asset` (プール投入) と満杯時の先頭戻しまでを**同一ロック内で
  完結**。cancelも同じロック内で (a) deque内の一致key破棄 (b) inflightの
  一致key破棄 (inflightをNoneへ差し替え) を行う。

ロック保持中の `enqueue_asset` は registryロック・poolキューロック取得と
非ブロッキングchannel送信のみ (完了チャネルはunbounded)のため安全。
ロック順序は常に backlog → registry → pool の一方向でデッドロックなし。
テスト用に**pop後・投入判定前に待機できる注入ゲート**
(`debug_arm_feeder_gate`。`set_failure_injection` と同じ
debug/devtoolsコンパイルゲート。IPC非公開・ハンドルdropで自動解放) を
追加し、決定論的インターリーブを再現した。

### R1: cancelがfeeder取り出し済みitemを見逃す (pop→submit窓)

上記構造で解消。cancelの `cancelled_backlog` はdeque内entryとinflightの
両方を計上 (キー単位で `not_found` 二重計上を排除 — 従来は「1件でも
破棄があると呼び出し内全キーのNotFoundを抑制」していた不正確さも修正)。
「cancelがnot_foundを返したキーがその後feeder経由でプールへ投入される
経路」は構造的に存在しない (cancel後の新規ユーザー要求は別需要)。
- red: `cancel_discards_feeder_inflight_item_in_pop_to_submit_window`
  — 修正前はpop→submit窓のcancelが `cancelled_backlog: 0, not_found: 1`
  を返し、解放後に当該assetが投入された (queue_depth 3)。
- green: 同テストが `cancelled_backlog: 1, not_found: 0`・不投入
  (queue_depth 2)・readyに当該id不在を検証。

### R2: 旧世代itemの新世代開始後の投入 (generation検査がsubmit後)

投入区間内で世代検査をプール投入**前**へ移動 (従来は計算/再キュー制御
のみで投入自体は無条件)。満杯先頭戻しも同一ロック内で行うため
「検査→戻し」間の置換もraceなし。
- red: `feeder_never_submits_stale_generation_item_after_new_request_all`
  — 修正前はゲート停止中の新世代request_all後も旧世代itemが投入された
  (queue_depth 3≠2)。
- green: 同テストが旧世代item不投入・readyに旧世代id不在を検証。

### R3: manifest所有確認→unlink競合 (ユーザーファイル削除TOCTOU)

**方針: 一切unlinkしない**。正規名 `export-manifest.json` が空きなら
NOREPLACE公開。占有されていれば (ユーザーファイル・GEN-TO自身の旧manifest
を問わず) 回避名 `export-manifest-{run uuid}.json` へNOREPLACE公開し、
既存は不接触。`manifest_is_gento_owned` (所有確認) と置換unlink経路を
削除。結果DTOの `manifestPath` が実際のパスを報告 (既存規約どおり)。
api-contract §48を「削除は一切しない」に正確化 (再実行で回避名manifestが
蓄積するのは方針の帰結として明記)。
- red (旧実装に新テストを当てた一時復元で実証):
  `manifest_never_replaces_even_gento_owned_file` /
  `manifest_published_atomically_without_tmp_leftovers` 再実行部 —
  旧実装は自前旧manifestをunlink置換 (正規名が最新で上書きされる)。
- green: (a) ユーザーファイル占有→回避名+ユーザーファイル不変
  (`manifest_never_overwrites_user_owned_file`) (b) 自前旧manifest占有→
  回避名・旧は残置・新manifestは最新run内容
  (`manifest_never_replaces_even_gento_owned_file`) (c) 空き→正規名
  (`manifest_published_atomically_without_tmp_leftovers` 前半)。
