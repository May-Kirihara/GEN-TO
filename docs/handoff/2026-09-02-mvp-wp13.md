## 実装概要

### 1. gento-db `backup.rs` (新規、コア実装)

- **フルDBバックアップ** `full_db_backup(db, dest_dir)`:
  `VACUUM INTO` は同ディレクトリ内の**一時名**
  (`{最終名}.tmp-{pid}`) へ書き出し → 単独接続でintegrity_check検証 →
  `sync_all` → 最終名へ**原子的リネーム**で公開する。
  - クラッシュや中断が最終名の世代を汚さない (残るのは一時名の残骸のみ。
    一時名は `list_full_backups` が `.tmp-` を含む名を除外するため
    retention・復元対象外)。
  - **原子rename ≠ durable publication**: renameは可視性の原子性のみ
    保証するため、公開前にデータ`sync_all`、公開後に親dirのsync
    (best-effort) を行う。検証・同期・renameの失敗はいずれも一時名を
    掃除して最終名を出さない。
  - **クラッシュ後の永続性はFS/プラットフォーム依存** (FG-WP13-2 N3
    明記): renameの原子性 (最終名には完全な世代のみが現れる) は保証
    するが、クラッシュ・電源断後に**そのrename自体が生き残るか**は
    親ディレクトリエントリのsyncが成功しているかに依存する。親dirの
    `sync_all` はbest-effort (一部FSではdir syncがno-op・エラーになる)
    ため、durabilityは基盤FSの保証範囲に従う。ポータブルバックアップ
    の公開 (`publish_dir`) も同じ性質。
  - 出力: `{dest}/library-full-{YYYYMMDDTHHMMSSmmmZ}.sqlite3`
    (タイムスタンプ先行固定幅 = 辞書順が時系列。migration用
    `library-pre-*` とは接頭辞で分離)。
  - 保持世代数は `app_settings` `backup.retention_generations`
    (既定3・不正値は既定)。同一ミリ秒連続作成は `-N` suffixで回避
    (VACUUM INTOは既存ファイルへの書き込みを拒否するため)。
  - **VACUUM INTOはreader接続の `PRAGMA query_only` に拒否される**ため、
    専用の短命接続 (`open_backup_conn`) で実行する。writerロックを
    長時間専有しない (Db並行性方針準拠)。
- **自動バックアップ** `auto_frequency` / `run_auto_backup_if_due`:
  `backup.auto_full_db` = `off`(既定)/`daily`/`weekly`。前回実行は
  `backup.last_auto_run` (epoch ms文字列・内部キー)。期限チェックは
  設定読み取りのみで軽量。
- **ポータブルバックアップ** `create_portable_backup(db, root_id, dest_parent)`:
  - 構成 = ディレクトリ形式 (PM設計どおり。単一アーカイナ却下の理由は
    api-contract §47記載)。
  - `metadata.jsonl`: asset行 (保守メタデータ + tags + 現行captions) +
    file行 (rel_pathは百分号エスケープ正準形 — 非UTF-8バイト完全保持)。
  - `collections.json`: 全コレクション (manual itemsはasset uuid参照、
    smartのquery_jsonは保存済み正規JSONをそのまま)。
  - 各ファイルは書き出し後に`sync_all` (durable publication)。tmpディレ
    クトリもsync (best-effort) してから `backup-info.json` を**最後に**書き、
    `.gento-tmp-{uuid}` から `{root名}-{ts}.gento` へ原子的リネーム。
    同一名存在時は連番suffix (無断上書きしない)。**rename失敗時もtmpを
    掃除する** (書き出し失敗以外もカバー)。
- **検証** `open_portable_backup(dir)`: `.gento`は**敵対的入力**
  (digestはバックアップ自身が再計算可能なため、整合性だけでは防御に
  ならない)。以下を強制する:
  - tmp残骸拒否・info欠落拒否・`format_version > 1` 拒否
    (`migrate_to_current` フックあり。現状v1のみ)・`complete != true` 拒否。
  - **file_digestsは必須2ファイル (`metadata.jsonl`/`collections.json`) の
    過不足なし一意** (欠落・重複・未知名は拒否 — 部分集合では
    collections.jsonなどが認証されずに済むため)。
  - **バックアップディレクトリの実ファイルが期待集合 (上記2つ +
    backup-info.json) と完全一致** (manifestに無い実ファイル = 改竄として
    拒否)。ディレクトリ列挙は1件でもエラーなら即失敗 (FG-WP13-2 N1 —
    fail-closed。黙って除外すると検証されていない実体が混入し得る)。
  - **backup-info.jsonの件数が実解析行数と一致** (info自体はdigest対象外
    のため、申告改変はこの検証でのみ検出)。
  - **asset/file/collection UUIDの重複拒否** (自己再digestバックアップが
    同一UUIDを行複製する改竄を排除。file UUID重複もFG-WP13-2 N2で
    テスト追加 — 実装は従来から拒否)。
  - 全ファイルBLAKE3 digest再計算一致検証。
- **パス検証 (rel_path)**: 復元側はすべてのrel_pathを
  `decode_rel_checked` で解釈する。絶対パス (unix `/`・windows prefix)、
  `..` 親コンポーネント (percent-encoded `..` も復号後に同一判定)、
  windows prefixの文字列表現 (`C:` drive / `\\` UNC — 現行linux開発でも
  拒否)、NUL、空・`.`のみを拒否し、`.`を正規化除去した
  `Component::Normal` のみの相対パスへ再構成してからrootへjoinする
  (検証はこの単一関数に集約)。
  - **symlink方針 (FG-WP13-2で強化)**: フォローしない —
    **中間コンポーネント含む全経路**を `gento_core::open_regular_beneath`
    (新module `gento-core/src/path_safety.rs`) で歩行する。Linuxは
    `openat2(2)` + `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS` の単一原子
    呼び出し (ENOSYS/EINVALは非対応扱いでフォールバック)、非対応
    カーネルと非Linux unixは `openat` + `O_DIRECTORY|O_NOFOLLOW` の
    fd歩行 (中間symlink = 即エラー、fdは毎ステップ入れ替えでパス
    差し替え耐性)。経路は一度だけ解決されるため開いたfdのfstatが正本
    (旧実装の「検査時statとopen後fstatの (dev, ino) 突き合わせ」は
    二重解決が不要になり廃止)。`root/linked-dir/image.png`
    (linked-dir = ルート外symlink) はplan時点で行方不明、実行でも
    登録しない。最終コンポーネントのsymlink拒否 (FG-WP13-1) は維持。
    非unix (Windows) は字句的symlink検査フォールバック (race-freeでは
    ない — WP-17で再検討)。
- **復元plan** `build_restore_plan(db, backup, target_root_id)`:
  マッチング優先度 **UUID → content_hash → rel_path**。
  - `Uuid`: uuid一致かつhash同一 → same/update判定 (rating/triage/favorite/
    タグ正規化名集合/現行caption bodyの完全比較)。
  - `Hash`: hash一致 (パス移動後の再関連付け)。**presentファイルが
    2箇所以上なら `Ambiguous` としてスキップ** (推測して適用しない)。
  - `PathAdd`: DBに無いがディスクの同パス実体をhash検証して一致 → add。
  - `Conflict`: 同一UUIDに別内容 / バックアップのパス位置に別内容
    (DB行またはディスク実体)。
  - `Missing`: 現DBにもディスクにも無い (または状態不明・検証不能)。
  - 在不在判定は `symlink_metadata` 3分類 (`Path::exists` 不使用 —
    権限エラーでもfalseになるため)。
- **復元実行** `execute_restore(db, backup, confirmed_plan, expected_digest)`:
  **確認トークンに束縛された確定plan**を適用する。
  - 適用は単一writerトランザクション (`unchecked_transaction`) 内で
    **現状からplanを再計算**し、`restore_intent_digest` が
    `expected_digest` (確認時の値) と一致する場合のみ行われる。
    確認から適用までの間にDBが変化していれば `RestoreError::PlanChanged`
    としてトランザクションごと中止 (DBは無変更)。
  - Update: rating/triage/favorite更新 + タグ併合 (正規化名で既存統合、
    現DB側タグは削除しない) + caption現行入れ替え (旧現行は履歴current=0へ
    降格。source/manually_editedはバックアップ保存)。
  - Add: asset作成 (UUIDはバックアップ保存 — 次回UUID一致のため。
    衝突時のみ新規UUID) + 検証済みon-diskファイルのfile行作成
    (実行時にもsymlink検査+fd照合+hash再検証 — plan後に実体が変わった
    ものは登録しない)。
  - コレクション: uuid一致→項目マージ (冪等) / 無ければ作成
    (smartはquery_jsonをparse_storedで検証してから保存)。
  - FTS: 触ったassetの文書を `rebuild_docs_for_assets` (WP-8経路) で再構築。
  - **現DBのデータは削除しない** (追加・更新のみ — データ損失面の安全設計)。

### 2. gento-tauri `backup.rs` (command層)

- `BackupService`: 確認トークンゲート (fileops.rsの
  `ConfirmTokenStore` を pub(crate) 化して再利用 — 同一方式)。
  - `restore_plan` → plan + トークン発行 (意図ダイジェスト
    `restore_intent_digest` に束ねる)。
  - `restore_execute` のシーケンス (FG-WP13-1 B2 — 確認と適用のTOCTOU
    閉塞。plan→execute間のDB変化は実行されない):
    1. 実行時点でplanを再計算し、意図ダイジェストがトークン発行時と
       一致することを確認して**トークンを消費する** (単発・5分失効。
       不一致/流用/再利用は全て拒否)。
    2. 消費済みトークンが保証する**確定plan**を gento-dbの
       `execute_restore` へ渡す。適用トランザクション内で現状からplanを
       再計算してdigest一致を再検証するため、手順1と適用の間のDB変化は
       `RestoreError::PlanChanged` (UI: 「確認の後にライブラリの状態が
       変化しました。計画をやり直して…」) で中止される。
  - 意図ダイジェスト = backup集約digest + root uuid + 対象root id +
    全entry (uuid, match種別, action, 解決済みasset id, content_hash,
    file rel_path [backup正準形+現DB解決形]) 昇順 + summary件数 +
    コレクション (uuid, will_create, 項目数, 解決可能項目数) 昇順を
    長さ前置連結してBLAKE3 (fileops.rsのcanonical_intent_inputと同じ
    曖昧さ排除)。表示用フィールド (reason/display_name/on_disk) は
    同値判定から意図的に除外。
  - 自動バックアップ背景ループ (`start_auto_loop` / `shutdown`):
    起動時即チェック → 1時間毎 (10秒分割sleepでshutdown応答性確保)。
    既定offのため何もしない。
- Commands (async + spawn_blocking・DTOはcamelCase — §46規約):
  `backup_portable_create` / `backup_full_db` / `backup_default_dir` /
  `backup_restore_plan` / `backup_restore_execute` /
  `backup_settings_get` / `backup_settings_set`。
  debug/release両方のinvoke handlerに登録 (計測機能ではないため)。

## 設計判断・逸脱

- **逸脱なし** (PM設計1-8に従う)。DB migration不要 (app_settingsで足りた)。
- FG-WP13-1 (レビュー対応): 4 blocker (rel_pathトラバーサル / 確認トークン
  TOCTOUと意図digest弱さ / フルDB公開のクラッシュ原子性 / digest manifest
  完全性) とnon-blocking 4件 (rename失敗時tmp掃除・durable publicationの
  sync_all・件数一致検証・`uuid_free`の固定テーブル名) を修正。
  `execute_restore` の公開シグネチャを
  `(db, backup, confirmed_plan, expected_digest)` へ変更 (確認済みplanの
  適用を型で強制) し、`RestoreError` を新設した。
- FG-WP13-2 (レビュー対応): 残blocker 1件 (中間ディレクトリsymlink脱出 —
  最終コンポーネントのみの検査では `root/linked-dir/image.png` 型の脱出を
  防げない) を `gento-core` の新プリミティブ `open_regular_beneath` で
  修正。**経路を一度だけ解決するfd歩行のため (dev, ino) 突き合わせは
  廃止** (二重解決のpin比較は不要になった — 開いたfdが正本)。
  non-blocking 3件も同時対応: N1 ディレクトリ列挙fail-closed、
  N2 file UUID重複テスト、N3 rename原子性とdurabilityの境界の明記
  (上記フルDBセクション)。`libc` 0.2系をgento-coreへ直付け
  (dependency-notes FG-WP13-2項に記録)。
- `ConfirmTokenStore` を fileops.rsで `pub(crate)` 化 (振る舞い無変更。
  WP-13で同一パターンを共用するための最小変更)。
- 曖昧 (同一hash複数箇所) の判定は「hashマッチ時の present file行数 ≥ 2」
  とした。UUID一致は identity確定のため曖昧扱いしない (保守的な線引きは
  PM指示「推測して適用しない」に準拠)。
- 復元のUpdateはバックアップ時点へ**上書き**する (復元の意図どおり)。
  planが差分を表示し確認トークンでゲートするため予測可能性を担保。
  タグに限り現DB側を削除せず併合 (手作業の喪失リスクを避ける)。

## 残課題・次WPへの申し送り

- 復元実行のAdd経路はトランザクション内でon-disk hashを再検証し、
  さらに適用tx内でplan全体を再計算するため、大量追加時はwriter接続を
  長時間保持し得る (正確性優先の意図的な選択)。大規模運用で問題になる
  場合は バッチcommit + resume 方式の検討。
- plan構築は現DB全体のassets/filesを読む (5万件想定で単一スキャン)。
  進捗イベント・キャンセルは未実装 (api-contract §47に将来課題と記載)。
- 復元のターゲットルートはuuid一致→単一ルートの自動解決のみ。複数ルート
  環境での明示選択UIは RestoreDialog に `targetRootId` を渡せば backend側
  対応済み (WP-15のUI本格化で接続)。
- E2Eドライバ (scripts/) への追加シナリオは本WPでは未実施 —
  cargo/vitest レベルで機能は検証済み。実機E2Eは既存回帰のみ確認。
- `backup_settings_set` のUIは WP-15設定画面で本格化 (commandは実装済み)。
- rel_path検証はbackslashを含むunixファイル名を許容する (正当なファイル名
  のため)。Windowsネイティブ対応 (WP-17) の際はbackslashの扱いを再検討
  (prefix表現の拒否は維持)。
