## 概要

コピー・移動・リネーム・新規フォルダ・ゴミ箱・完全削除を、計画 (dry-run) →
確認 → 実行 → 操作ログ確定 → 通知 の実行モデルで実装した。**ユーザー
データを初めて変更・削除するWP**のため、安全原則5項目をコード構造で強制し、
ファイル単位の部分成功・協調キャンセル・Undo前提検証・異常終了回復を
単体テスト (cargo +49) と実機E2E (12項目) で証明した。

## 安全原則の実装対応表 (計画書§15 → コード/テスト)

|---|---|---|
| 1. 通常削除はゴミ箱 | `FileOpKind::Trash` が既定削除。`DeleteForever` は別コマンド (UI: Shift+Delete + 確認ダイアログ + 「完全に削除する」チェックボックスの2段)。ゴミ箱失敗時の通常削除フォールバックは**禁止** (`gento_platform::trash_to_bin` はエラーのみ返す) | core `execute_trash_failure_keeps_everything_untouched` (元ファイル・DB無傷のロールバック検証)、tauri `real_file_ops_trash_missing_is_error_without_fallback`、E2E 6/8 |
| 2. 上書きは明示確認 | dry-run (`plan_file_op`) が衝突を検出 (同名・容量・mtime・**ハッシュ一致**)。`ConflictResolution::Overwrite` 明示時のみ置換。**未指定の衝突はskip (安全側)**。「操作先==操作元」の上書きは実行拒否 | core `execute_copy_conflict_overwrite_replaces` / `execute_copy_overwrite_onto_itself_refused`、fileops.test.ts 全解決組み合わせ (3方針³ × 単発/apply_all)、E2E 2 |
| 3. 外部変更で前提が崩れたUndoは拒否 | `verify_undo`: 全ステップ all-or-nothing で (対象の存在・世代トークン `(os_file_id,size,mtime_ns)` 一致・戻し先の不在) を検証し、1つでも崩れていれば**何も実行せず**理由 (`UndoRefusal::describe`) を返す | core `undo_refuses_when_file_modified_after_operation` / `undo_refuses_when_destination_recreated` / `undo_all_or_nothing_when_batch_has_one_broken_step` / `undo_missing_file_refuses_with_reason`、tauri `service_undo_check_reports_external_modification`、E2E 4 |
| 4. コピー完了前のファイルを正規ファイルとして登録しない | コピーは宛先ディレクトリ内のテンポラリ名 `.gento-tmp-<uuid>-<name>` で書き込み → fsync → 最終名へ **rename後にDB反映**。走査側 (`gento-image is_image_entry`) も同接頭辞を画像扱い**しない** (異常終了残骸も一覧・DBに出ない)。起動時に `.gento-tmp-`を掃除 (`sweep_tmp_files`) | core `copy_tmp_not_registered_midway_and_final_named_after` (テンポラリ実在中のDB不在を観測フックで証明)、image `is_image_entry_rejects_gento_tmp_in_progress_files`、tauri `real_file_ops_cancel_mid_copy_removes_tmp` / `recovery_finalizes_executing_ops_and_sweeps_tmp` |
| 5. 操作ログを確定してからUI上の成功を通知 | 実行は (a) file_operations行を`executing`で確保 → (b) ファイル単位FS+DB (1tx) → (c) result JSON (全ファイル成否) 書き込み+status確定。Tauri commandはこの**確定後**の応答を返し、フロントは応答でトースト表示 | core `file_operations_recorded_once_with_request_and_result` (1論理操作=1行・request/result JSON形状)、tauri `service_copy_flow_with_real_db_and_suppression` (operation_finishedが実行後に1回) |

## 設計判断 (報告要件)

1. **watcher抑制方式**: WatchBuffer (gento-core) へパス抑制キーを追加し、
   操作実行前にsrc/dstを登録・DB反映後に解除 (`FileOpsService::execute`)。
   キー照合 (パス単位) 方式を採った理由: (a) 「アプリ内操作中」フラグ方式
   は長時間コピー中のユーザー外部操作まで失う、(b) 走査の冪等性により
   抑制漏れ (解除後のstragglerイベント) は無害 — 安全側は据え置き。
   Undo時も逆操作パスを同様に抑制。テスト: core
   `watch_buffer_suppresses_self_operation_paths` + tauri
   `service_copy_flow_with_real_db_and_suppression` (登録/解除の呼び出し
   検証) + E2E 3 (移動後3秒待っても行が1行のみ = 二重反映なし)。
2. **ゴミ箱のDB扱い**: ゴミ箱/完全削除/ルート外移動はすべて `missing` 化
   (再出現で復帰)。`.gento-trash` 仮想化はしない — WP指示どおり。
   完全削除もmissing化 + **Assetは残す** (RESTRICT。hash共有再利用可)。
   上書き破壊された旧ファイルの行のみ `delete_file` で削除
   (UNIQUE (root,rel_path) を新行へ明け渡すため。Asset自体は残存)。
3. **Undo前提検証**: 世代トークン `(os_file_id, size, mtime_ns)` (WP-2と
   同一組成) をresult JSONへ保存 (`TokenDto`)。Undo実行前に全アクション
   を検証 (all-or-nothing — バッチの一部だけ戻す不整合を構造的に排除)。
   コピーのUndo = 生成物を**ゴミ箱へ** (即削除しない — 誤操作でも復帰可)。
   ゴミ箱のUndo = `restore_from_trash` (trash crateに単一項目復帰APIが
   ないためXDG trashinfo仕様に基づく自前実装。trash crateの配置と
   往復はgento-platformテスト+E2Eで実証)。
   留意: request/result JSONのパスはlossy UTF-8 (非UTF-8パスの
   クロスセッションUndoはトークン/パス不一致で安全に拒否される —
   fails closed)。
4. **DBトランザクション**: ファイル単位で1tx (FS成功→reflect_db)。
   FS成功・DB失敗時はステップを失敗報告 (黙って成功としない) し再スキャン
   で収束。操作全体のstatusは全ステップ成否から導出 (done/partial/failed)。
5. **計画→実行の信頼境界**: `file_ops_execute` はクライアントから計画を
   受けず**入力 (kind/paths/dest/解決方針) から再計画**する (改竄された
   計画の実行を構造的に排除)。
6. **実行排他**: `running` ロックで同時1操作 (二重実行拒否)。
   キャンセルはAtomicBool協調 (ファイル境界+コピーchunk境界)。

6. **コピーのmtime保存**: RealFileOpsのコピーは元ファイルのmtimeを保存

# FG-WP7 追記: Codexレビューブロッカー7件修正 (2026-08-31)

Codexレビュー (`/tmp/codex-mvp-wp7-review.md`, verdict: reject) のブロッカー
7件を全件修正した。方針は「破壊的操作の安全性ゲートを**構造**で強制する」
— UIの確認ではなくbackend/FS契約で強制する。

## ブロッカー別修正内容

### 1. 恒久削除のbackend確認ゲート
- `FileOpsService` (gento-tauri) に `ConfirmTokenStore` を追加: `plan` が
  `kind: delete_forever` または衝突を含む計画に対し**単発トークン**
  (uuid nonce・メモリ保持・5分失効・1回限り) を発行し `FileOpPlanDto
  .confirm_token` へ返す。`execute` は delete_forever / overwrite解決の
  実行にトークン一致を**必須**化 (不一致・失効・再利用はErr。消費で破棄)。
- UI (App.svelte): 完全削除は 計画→DeleteForeverDialog(チェックボックス)
  →トークン付き実行 に更新。衝突ダイアログフローも計画時トークンを携带。
  再試行はトークンが単発のため再計画から (`runPlannedOp` 経由に変更)。
- テスト: `confirm_token_gate_delete_forever` (無し拒否・不正拒否・正常・
  再利用拒否) / `confirm_token_expires_after_ttl` (失効拒否) /
  `confirm_token_gate_overwrite_resolution` (上書きにも必須・keep_bothは
  不要) / `confirm_token_not_issued_for_non_destructive_plan`。

### 2. 上書きTOCTOUの排除 (no-clobber)
- **最終配置はすべてreplace禁止の原子操作**: gento-platformに
  `rename_noreplace` を追加 — Linux `renameat2(RENAME_NOREPLACE)` 直接
  syscall (libc。**nix不採用**: 必要なのは単一syscallのみで依存最小化。

  keep_both代替名) が作成されていたら AlreadyExists 失敗 (ユーザー再計画)。
- テスト: core `execute_refuses_destination_created_after_plan_copy_and_move`
