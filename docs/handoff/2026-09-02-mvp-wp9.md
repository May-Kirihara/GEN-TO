## 構成 (追加・変更の要点)

### gento-image: `metadata` モジュール (新設・24テスト)

- `mod.rs`: fd束ねエントリポイント `hash_probe_metadata_file`
  (ハッシュ→プローブ→メタデータ抽出、前後fdトークン照合) と
  `reparse_metadata_file` (再解析用・ハッシュなし)。`CURRENT_PARSERS`
  (名前, version) が再解析判定の正本
- `png_chunks.rs`: tEXt/iTXt/zTXt/eXIf収集の自前チャンク走査
  (**1チャンク4MiB・合計16MiB上限**、超過は警告付きスキップ → raw JSONの
  `__warnings` に記録されUIから見える)。zTXt/iTXt圧縮はflate2
  (png crate経由で既にlock内) で解凍 — 解凍出力にも同じ上限
- `exif.rs`: kamadak-exifで正規化 (taken_at RFC3339化・カメラ/レンズ・
  GPS DMS→十進度 S/W負・orientation) + 全フィールドの `raw_exif` JSON
  (1フィールド2048文字・1024フィールド上限)。TIFF/WebPはcrateの
  `read_from_container` (読み取り総量64MiB上限のRead+Seekラッパで包む)
- `iptc.rs`: APP13 8BIM内IIMの最小自作解析 (title/keywords/byline/
  copyright/caption/writer + 未知datasetは `r:d` 生キーでraw保持。
  拡張長形式・マルチセグメント・ malformed tail許容)
- `gen.rs`: sd-params (引用符内カンマを含むparams行の分解に耐性) /
  comfy (KSampler→positive/negativeの接続追跡。ConditioningCombine等
  の既知条件ノードを再帰走査、`workflow`はraw_workflowへverbatim) /
  nai (Comment JSON + Description/Software/Source)
- fixturesは**すべてRustテストコード内で手組み生成**
  (`metadata/test_support.rs` — TIFF/チャンク/IIMバイナリを直接構築。
  外部ファイル非依存・決定的)

### gento-db: `assetmeta.rs` (新設) + search.rs拡張

- `save_asset_metadata`: 同version行は冪等スキップ、version違いは置換。
  positive_prompt (優先順位 sd-params > comfy > nai) を `embedded_prompt`
  キャプション (source=embedded_metadata) として同一txで書き、文書再構築。
  **手動編集済み現行行は上書きしない** (仕様§10保護の回帰テスト付き)
- `assets_needing_reparse`: (a) 行ゼロ (b) 既存行のversion不一致 (c) 廃止
  parser名の行 — **「全parser行の存在」は要求しない** (形式ごとに行構成が
  異なるため。parser集合変更は全version繰り上げの運用とセット)
- FTS文書のcaptions列へ `embedded_prompt` 接続 (WP-8の申し送り実装)。
  negative prompt・workflow全体は含めない (data-model §9)
- 検索field keys: `model` `sampler` `vae` `lora` (部分一致・EXISTS) /
  `steps` (数値比較) / `has:workflow` (raw_workflow IS NOT NULL)。
  loraはJSON1 (`json_each(json_extract(generation_extra,'$.loras'))`) で照合

### gento-tauri: metadata.rs拡張

- `asset_metadata_get(assetId)` (async・spawn_blocking): parser行DTO +
  マージ済み正規化DTO (`merge_normalized` — 写真系=exif、生成系=
  sd-params > comfy > nai の優先順位)
- `metadata_reparse()` (async): 1回最大500 assetをバッチ再解析
  (進捗 `metadata:reparse_progress`)。代表presentファイルのfdでトークン

- 統合テスト: 実ファイル (SD parameters PNG) を登録ルート経由でリンク →
  再解析で行保存・DTO取得・2回目対象なしを検証

### E2E開発中に発見・修正したドライバ/ジェネレータのバグ (記録)

1. 初版ジェネレータがPNGの**チャンクタイプにkeywordを書いていた**
   (tEXtで包まず `parameters` 型チャンク)。パーサは正しく無視した —
   プロダクト側ではなくフィクスチャ側のバグ。PIL生成に切り替えで解決。
2. ドライバのS行パースが `S act=1 tot=N` を想定していたが実際は
   `S act=1 q="..." tot=N` (q=が間に入る) のため全検証が不一致になっていた。
   `stot()` ヘルパで修正。

## 設計判断の記録

- **embedded_promptキャプション経由でFTS接続** (asset_metadata直接JOINで
  なく): WP-1で設計済みのcaptions kind (source=embedded_metadata) を使用。
  手動編集保護・履歴形式を既存のset_captionと共有
- **再解析候補は「行ゼロ or version不一致 or 廃止parser行」**: 形式ごとに
  生成される行が異なる (JPEGはpng-text行を持たない) ため「全parser行の
  存在」では判定できない。parser集合の変更 (追加・削除) は**全parserの
  version繰り上げ**で全assetを再解析対象化する (冪等スキップで実際の
  書き換えは変化した行のみ)
- **positive_promptの複数形式混在時の優先順位**: sd-params > comfy > nai
  (1ファイルに複数生成形式が混在する敵対的ケースの決定論化)
- **GPSは緯度・経度・方向参照が揃って初めて正規化** (片側のみ・方向不明は
  破棄。rawには残る)
- **zTXt/iTXt圧縮の解凍出力にも上限** (flate2をtake()で包む — 圧縮bomp対策)
- A1111のJPEG出力 (EXIF UserCommentへのparameters) は**非対応のまま**
  (WP指示がPNGテキストチャンクに限定)。AVIF EXIFも対象外。api-contract §43
  の既知の制限に列挙

## 既知の制限・次WPへの申し送り

- ComfyUI条件ノード解決は既知クラスのみ (未知ノードはunknown扱い =
  プロンプト抽出なし。rawのprompt JSONで確認可能)
- GPSのAI送信設定のUI接続はWP-10 (本WPでは「ルート単位」である旨の注記のみ)
- メタデータ再解析の本格ジョブ基盤 (キューイング・再試行) はWP-10。
  現状は `metadata_reparse` コマンドのバッチ実行 (1回500 asset)
- 巨大workflow (16MiB級) のIPCペイロード: `asset_metadata_get` は全rawを
  一度に返す (折りたたみで**レンダリング**は保護されているが転送は丸ごと)。
  レイテンシが問題になったらスロットット別取得へ分割する案を残す
- E2Eのclipboard検証は「コピー発火と文字数」まで (OSクリップボードの
  実内容検証はwebview権限の外)
