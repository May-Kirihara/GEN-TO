## 1. 目的

技術スパイクで成立を確認した画像一覧、ビューア、比較表示、サムネイル基盤を製品コードへ発展させ、以下を一貫して利用できるMVPを完成させる。

> ディレクトリ型画像ファイラーとして高速に閲覧・選別でき、登録フォルダではタグ、生成メタデータ、AIキャプション、自然言語検索、コレクション、バックアップ、SD学習用エクスポートを利用できるデスクトップアプリ。

本計画は機能を単独で並行実装するのではなく、動作する縦方向の単位を段階的に積み上げる。各ワークパッケージ（WP）は、テストと受け入れ条件を満たしてから完了とする。

## 2. MVP完了条件

### 2.1 ユーザー機能

- 未登録フォルダを通常の画像ファイラーとして閲覧できる
- 複数の登録ルートを追加、解除、再スキャンできる
- JPEG、PNG、WebP、GIF、BMP、TIFF、AVIFを閲覧できる
- サムネイル一覧、単一ビューア、2枚・4枚比較を利用できる
- コピー、移動、リネーム、新規フォルダ、ゴミ箱、可能な範囲のUndoを利用できる
- 星評価、採用・除外、お気に入り、タグ、キャプション、メモを保存できる
- 手動コレクションと基本的なスマートコレクションを利用できる
- EXIF、IPTC、主要なPNG生成メタデータを読み取り表示できる
- OpenAI互換Vision APIでタグとキャプションを自動生成できる
- ruri-v3とUSearchで自然言語検索できる
- キーワード、タグ、条件、意味検索を組み合わせられる
- メタデータをバックアップ・復元できる
- 画像と同名の`.txt`を含むSD学習用データセットをエクスポートできる

### 2.2 品質

- LinuxでMVPの全受け入れ試験を通過する
- Windowsで主要ユーザーフローと性能ゲートを通過する
- macOSは可能な範囲でビルド可能性を確認し、正式対応可否を記録する
- DB、キャッシュ、ファイル操作の異常終了から復旧可能
- 元画像へEXIF、IPTC、アプリ固有情報を書き込まない
- AI処理中もファイル閲覧と選別を妨げない
- すべてのDB変更をマイグレーション管理する
- セキュリティ上重要なローカルプロトコルとファイル操作に回帰試験がある

## 3. MVP非対象

- 見開き、右綴じ、ZIP、CBZ
- PSD、Clip Studio Paint、RAW、HEIF／HEIC、OpenEXR、HDR、PDF、動画
- OCR
- 画像埋め込みによる視覚類似検索
- ピクセル一致および類似画像の完成版整理UI
- ComfyUIへの直接送信
- 画像群への質問応答型RAG
- クラウド同期、複数端末同期
- 元画像へのEXIF／IPTC書き込み
- プラグイン機構
- 完全なタグ階層・多言語オントロジー

## 4. 採用技術

- Tauri 2
- Svelte 5、TypeScript、Vite
- Rust workspace
- SQLite、WAL、FTS5
- BLAKE3
- USearch HNSW
- ONNX Runtime
- ruri-v3-70m（標準）、ruri-v3-30m（軽量）
- OpenAI互換API

スパイクで採用したTanStack Virtual、Rust画像処理、WebPキャッシュ、優先度付きワーカープール、制限付きローカルプロトコルを継続利用する。依存ライブラリの具体名は各WP着手時に、ライセンス、保守状況、対応OSを確認して記録する。

## 5. 目標workspace

```text
crates/
├── gento-core        # ドメイン型、ユースケース、抽象インターフェース
├── gento-db          # SQLite、migration、repository
├── gento-image       # 走査、probe、decode、thumbnail、metadata
├── gento-search      # FTS、検索式、ranking、USearch
├── gento-ai          # OpenAI互換API、プロンプト、AIジョブ
├── gento-embedding   # tokenizer、ONNX、埋め込みプロバイダー
├── gento-platform    # ゴミ箱、OSファイルID、資格情報ストア等
└── gento-tauri       # 薄いTauriアダプター

apps/
├── desktop           # Svelte UI + src-tauri
└── embedding-worker  # 独立した埋め込みワーカー
```

循環依存を避け、`gento-core`はDB、Tauri、ONNX、HTTPクライアントへ依存しない。外部機能はtraitを介して注入する。

## 6. 実装原則

- SQLiteをメタデータの正本とする
- サムネイルとUSearchインデックスは再生成可能なキャッシュとする
- ファイルI/O、画像デコード、DB大量処理、AI推論をUIスレッドで行わない
- 画像内容（Asset）とファイル実体（File）を分離する
- 同一バイト内容のコピーはタグ、評価、キャプション等を共有する
- 外部へ持ち出すIDはUUID、DB内部は整数IDを使用する
- commandで巨大配列や画像バイト列を送らない
- 長時間処理は進捗、キャンセル、再試行、再開を持つ
- 元ファイル変更は明示的なファイル操作だけに限定する
- ユーザー編集済み情報をAI再生成で上書きしない
- 障害を個別ファイル・個別ジョブへ隔離する
- 性能最適化は構造化計測に基づく

## 7. リリース段階

```text
M0  スパイク製品化
M1  永続ライブラリと登録ルート
M2  ファイラーとメタデータ編集
M3  安全なファイル操作
M4  テキスト検索・コレクション
M5  画像メタデータ
M6  AIタグ・キャプション
M7  自然言語検索
M8  バックアップ・エクスポート
M9  クロスプラットフォーム・リリース候補
```

M0～M4でAIなしでも有用な画像ファイラーを成立させる。AI基盤が遅延しても通常機能を出荷可能な構造にする。

## 8. WP-0: スパイクから製品基盤への移行

### 目的

計測専用コードを整理し、既存性能を失わずMVP実装の土台を作る。

### 作業

- スパイクの全テストを基準値として固定する
- 開発ブリッジと障害注入をdebug／明示featureへ隔離する
- 仮想5万件モードを開発機能へ隔離する
- crate責務と公開APIを再確認する
- DTOにAPIバージョンまたは互換方針を導入する
- アプリデータ、キャッシュ、ログのディレクトリ解決を抽象化する
- 構造化ログとクラッシュ前後の診断情報を整理する
- 依存ライセンス一覧を生成する仕組みを用意する
- スパイク性能シナリオを継続実行可能に保つ

### 受け入れ条件

- 既存Rust 159件、フロントエンド218件以上のテストが成功する
- release性能がスパイク結果から大幅に退行しない
- release buildで危険な開発commandを呼び出せない
- データセットがなくても通常起動できる
- 次WPがスパイク専用状態へ依存しない

## 9. WP-1: SQLite基盤とマイグレーション

### 作業

- `gento-db` crateを追加する
- SQLite接続、WAL、foreign keys、busy timeoutを設定する
- schema versionと順方向migrationを実装する
- DB作成、正常終了、異常終了、バックアップ中の動作をテストする
- repository traitとSQLite実装を分離する
- UUID生成規則、日時形式、enum格納形式を固定する
- 以下の初期テーブルを作る
  - `library_roots`
  - `assets`
  - `files`
  - `tags`
  - `asset_tags`
  - `captions`
  - `collections`
  - `collection_items`
  - `asset_metadata`
  - `jobs`
  - `file_operations`
  - `embeddings`
- DB整合性検査と診断commandを用意する

### 重要設計

- pathは登録ルート＋相対パスを基本とする
- 非UTF-8パスを失わない表現を検証する
- Asset作成前でも走査中Fileを管理できる状態を用意する
- `missing`を削除と区別する
- migration失敗時に元DBを壊さない

### 受け入れ条件

- 空DBから最新schemaを作成できる
- 各過去migration fixtureを最新へ更新できる
- foreign key違反を検出する
- DBを閉じずにアプリを強制終了しても次回起動できる
- repository単体試験がTauriなしで動作する

## 10. WP-2: 登録ルート、永続カタログ、差分スキャン

### 作業

- 登録ルートの追加、無効化、解除を実装する
- 親子関係にある二重登録を警告する
- 初回スキャンと差分スキャンを実装する
- サイズ＋更新日時による高速変更判定を行う
- BLAKE3を低優先度で計算する
- 同一内容を同一Assetへ統合する
- OSファイルIDを利用可能な場合に保持する
- 外部移動、改名、不在、再出現を処理する
- フォルダ監視を追加し、イベント欠落時は再スキャンで収束させる
- スキャンとハッシュの進捗、停止、再開を実装する
- 未登録フォルダの一時閲覧と登録済みカタログを統合する

### 受け入れ条件

- 再起動後も登録ルートと一覧が復元される
- 追加、変更、改名、移動、削除をDBへ反映できる
- 同一バイト内容の複数ファイルが1 Assetを共有する
- 不在ファイルのメタデータを即時削除しない
- 外部監視イベントを大量に受けても最終状態が一致する
- 初回スキャン中も既存一覧を操作できる

## 11. WP-3: MVP画像形式と表示パイプライン

### 対象形式

- JPEG／JPG
- PNG
- WebP
- GIF
- BMP
- TIFF
- AVIF

JPEG XLとAPNGは依存基盤と実測を見て別ゲートで判断する。

### 作業

- probe、decode、thumbnail、previewの形式別adapterを作る
- EXIF Orientationを統一して反映する
- ICCプロファイル対応範囲を明記する
- GIF／WebPアニメーションの静止サムネイルを生成する
- 単一ビューアでのアニメーション再生を実装する
- 透過背景を市松、白、黒から切り替える
- 破損、不正寸法、デコード上限超過を安全に扱う
- WebP q80 previewが比較判断に十分か再評価する
- 必要ならpreviewだけ高品質または可逆形式へ変更する
- 形式別fixtureとfuzz／property test候補を整備する

### 受け入れ条件

- 全MVP形式を一覧、ビューア、比較で表示できる
- 不正画像で過大メモリ確保しない
- Orientationと透過が期待どおり
- アニメーションが一覧全体を高負荷にしない
- previewとoriginalの切り替えが視覚的に破綻しない

- OSファイルマネージャーで表示、外部アプリで開く、パスコピーを追加する
- ショートカット設定の基盤を作る
- 空、読み取り不能、オフライン、未対応状態を表示する
- 選別セッションと進捗保存を実装する

### 受け入れ条件

- 未登録フォルダをDB登録なしで閲覧できる

## 13. WP-5: 評価、選別、タグ、キャプション

### 作業

- 星0～5、採用／除外／未選別、お気に入りを実装する
- 一括編集とUndoを実装する
- タグ作成、追加、削除、候補表示、使用数を実装する
- タグ正規化規則を固定する
- 一般タグとSD用タグ列を分離する
- description、sd_tags、user_noteを編集できるようにする
- AI由来、手動編集済み、履歴を表示できるデータ構造にする
- 高速選別モードと自動次送りを実装する
- 2枚／4枚比較から採用・除外できるようにする

### 受け入れ条件

- 同一Assetを参照する複数Fileで論理メタデータを共有する
- 複数選択へ一括タグ・評価を適用できる
- 除外操作でファイルを削除しない
- ユーザー編集済みキャプションを明確に識別できる
- 編集中の異常終了でDBを不整合にしない

## 14. WP-6: 手動コレクションとスマートコレクション

### 作業

- 手動コレクションの作成、改名、削除を実装する
- Assetの追加、削除、任意並び順を実装する
- コレクション内メモを実装する
- 構造化検索式を保存するスマートコレクションを実装する
- コレクション単位の選別とエクスポート入口を作る

### 受け入れ条件

- コレクション操作で元ファイルを移動しない
- 同じAssetを複数コレクションへ追加できる
- スマートコレクションが元データ変更後に更新される
- SQL文をユーザーデータとして直接保存しない

## 15. WP-7: 安全なファイル操作とUndo

### 作業

- コピー、移動、リネーム、新規フォルダを実装する
- OSのゴミ箱を抽象化する
- 同名衝突UIを実装する
- 複数ファイルの部分成功を記録する
- `file_operations`へ操作前後を記録する
- 安全に可能な操作だけUndo可能にする
- 操作中の進捗、キャンセル、異常終了回復を実装する
- アプリ操作とフォルダ監視の二重反映を防ぐ
- シンボリックリンク、権限、別ファイルシステムを扱う

### 安全原則

- 通常削除はゴミ箱
- 上書きは明示確認
- 外部変更で前提が崩れたUndoは拒否
- コピー完了前のファイルを正規ファイルとして登録しない
- 操作ログを確定してからUI上の成功を通知する

### 受け入れ条件

- コピー、移動、改名後にDBとファイルシステムが一致する
- 衝突時に上書き、スキップ、両方保持を選べる
- 一括操作の部分失敗を再試行できる
- 異常終了後に未完了操作を検出し、安全に案内できる
- Undoで他の外部変更を破壊しない

## 16. WP-8: キーワード検索、FTS5、フィルター

- タグ、評価、選別、形式、日時、モデル等のfilterを実装する
- 検索結果をページングする
- 一致根拠を返す
- 保存済み検索とスマートコレクションを接続する
- 更新対象Assetだけを再索引化する

### 受け入れ条件

- 日本語と英数字を含む基本キーワード検索ができる
- GUI filterと検索構文を組み合わせられる
- 5万件規模でUIをブロックせず結果を返す
- indexを削除して再構築できる
- DB正本とFTSの不整合を検出・修復できる

## 19. WP-11: ruri-v3実行とモデル管理

### 作業

- `gento-embedding`と独立workerを追加する

### 受け入れ条件

- 一括埋め込み中もqueryを優先できる
- worker異常終了でメインアプリが終了しない
- モデル削除後も通常検索が動作する

## 20. WP-12: USearchとハイブリッド検索

### 作業

- 埋め込みをSQLite BLOBへ正本保存する
- source document hashで期限切れを検出する
- モデル／revision／次元別のUSearch indexを構築する
- SQLiteとindexのgenerationを比較する
- 差分反映と全再構築を実装する
- Rust正確検索フォールバックを実装する
- FTS、タグ一致、vector類似度を統合する
- ranking要素と検索根拠を返す
- モデル切り替え中は旧indexを維持し、完成後に切り替える

### 受け入れ条件

- 自然文から関連画像を検索できる
- USearch indexを削除してSQLiteから再構築できる
- 異なる次元を同じindexへ混在させない
- 埋め込み未生成画像もキーワード条件では検索できる
- hybrid rankingの各要素を診断表示できる
- USearch利用不能時に正確検索または通常検索へ退避できる

## 21. WP-13: バックアップと復元

### 作業

- SQLiteオンラインバックアップを実装する
- 登録ルート単位の`.gento`ポータブルバックアップを実装する
- metadata JSONL、collections、backup-infoを出力する
- UUID、相対パス、ハッシュを使った復元を実装する
- 衝突、行方不明、同一ハッシュ複数件を報告する
- バックアップversionとmigrationを実装する
- 自動バックアップ頻度と保存世代を設定可能にする
- 埋め込みを含めるか選択可能にするか、再生成扱いに固定する

### 受け入れ条件

- 新規DBへタグ、評価、キャプション、コレクションを復元できる
- パス変更後もハッシュで再関連付けできる
- 不完全バックアップを正常完了として扱わない
- 復元前に差分と衝突を表示する
- サムネイル、FTS、USearchをバックアップなしで再構築できる

## 28. セキュリティとプライバシー

- Tauri capabilityを最小化する
- ローカルプロトコルのAsset ID解決を維持する
- 外部URL、SVG等の能動コンテンツを初期対象にしない
- APIキーはOS資格情報ストアへ保存する
- AI送信は登録ルートと明示設定に限定する
- GPS送信は独立したopt-inとする
- 画像縮小後送信を既定候補とする
- Hugging Faceモデルは固定revisionとchecksumで検証する
- ONNXパッケージから任意コードを実行しない
- backup importを信頼せずschemaとサイズを検証する
- ファイル操作は正規化済みの明示対象だけへ行う

## 29. データ移行と互換性

- MVP開発中もschema migrationを追加方式で管理する
- DBを手編集前提にしない
- cache、FTS、USearchにはgeneration／algorithm versionを持たせる
- parser、prompt、embedding modelにもversionを持たせる
- 外部バックアップはversion付きschemaとする
- 破壊的migration前にはSQLite backupを作成する
- 古いモデルやindexは新しいものの完成後に削除する

## 31. ワークパッケージ運用

各WP開始時:

1. 関連仕様を読む
2. 現在のschema、API、テストを確認する
3. 実装範囲と非対象を短い作業メモへ記録する
4. 受け入れ条件をテスト項目へ変換する
5. 依存追加の理由とライセンスを確認する

各WP完了時:

1. formatter、lint、単体、統合テストを実行する
2. release buildを確認する
3. 関連文書を更新する
4. migrationとrollback／recoveryを確認する
5. 性能影響がある場合は基準シナリオを再計測する
6. 残課題を次WPへ暗黙に持ち越さず記録する
