# GEN-TO 埋め込みモデル実行・配布方針

- 文書状態: Draft
- 作成日: 2026-08-28
- 関連文書: [仕様草案](./spec-draft.md)、[データモデル草案](./data-model.md)

## 1. 採用方針

自然言語検索は初期状態では無効とし、ユーザーが設定画面から有効化する。

MVPでは以下を基準とする。

- 標準モデル: `cl-nagoya/ruri-v3-70m`
- 軽量モデル: `cl-nagoya/ruri-v3-30m`
- 実行形式: ONNX
- 実行エンジン: ONNX Runtime
- 実行場所: 独立したRustワーカープロセス
- MVPの実行デバイス: CPU
- ベクトルの正本: SQLite
- 検索インデックス: USearch HNSW

130mモデルは詳細設定から選択可能にする候補とし、310mモデルはMVP対象外とする。

Python、PyTorch、TransformersおよびSentenceTransformersはアプリへ同梱しない。

## 2. モデル選択UI

設定画面では以下を表示する。

- 自然言語検索の有効状態
- モデル名
- 出力次元数
- ライセンス
- 配布元
- ダウンロード容量と展開後容量
- 保存先
- ダウンロード状態
- モデルのロード状態
- 埋め込み済み件数と対象件数
- インデックス状態

初期選択肢:

| 選択肢 | モデル | 次元数 | 用途 |
|---|---|---:|---|
| 軽量 | ruri-v3-30m | 256 | 省メモリ、低性能環境 |
| 標準 | ruri-v3-70m | 384 | 既定値 |

有効化時は、Hugging Faceへの外部通信、必要な容量、ライセンスおよび既存画像の処理件数をユーザーへ提示する。

## 3. モデル配布

ruri-v3公式モデルを再現可能な手順でONNXへ変換し、元モデルとの出力誤差を検証した成果物をGEN-TO管理のHugging Faceリポジトリから配布する。

配布物の想定:

```text
model-package/
├── model.onnx
├── tokenizer.json
├── tokenizer_config.json
├── config.json
├── manifest.json
├── LICENSE
└── NOTICE
```

`manifest.json`には少なくとも以下を記録する。

- GEN-TOモデルパッケージのバージョン
- 元モデルのrepository ID
- 元モデルの固定commit revision
- 変換スクリプトのバージョンまたはcommit
- 各ファイルのチェックサム
- モデル種別
- 出力次元数
- 最大入力長
- 距離関数
- pooling方式
- 正規化方式
- 検索クエリと検索文書の接頭辞
- ライセンス情報
- 必要なONNX Runtimeバージョン

アプリはHugging Faceの`main`を無条件に取得せず、GEN-TOが検証した固定revisionを使用する。

第三者が変換したONNXモデルへ初期状態で依存しない。将来カスタムモデルを許可する場合は、標準モデルとは明確に区別する。

## 4. ダウンロード管理

- 進捗表示
- キャンセル
- 可能な場合は中断再開
- 空き容量の事前確認
- 一時ファイルへの保存
- 完了後のチェックサム検証
- 検証成功後のアトミックな有効化
- モデル削除
- 更新通知
- プロキシ環境の考慮

許可したONNX、JSON、tokenizer、ライセンス文書だけを読み込み、モデルパッケージから任意コードを実行しない。

ダウンロード失敗または検証失敗時は既存モデルを維持し、不完全なモデルを有効化しない。

## 5. 実行アーキテクチャ

```text
Tauri／Svelte UI
       ↓
Rustアプリケーションコア
       ↓
gento-embedding-worker
├── tokenizer
├── ONNX Runtime
├── mean pooling
└── L2 normalization
```

モデル推論をTauriのコアプロセスから分離し、専用ワーカーで実行する。

目的:

- 推論エンジンの異常からメインUIを隔離する
- モデルを明示的にロード・アンロードする
- メモリとCPU使用量を監視する
- 推論処理をキャンセルしやすくする
- 将来の実行エンジン交換を容易にする
- CLI等から同じ機能を利用可能にする

ワーカーとの通信にはローカルソケットまたは標準入出力を使用する。通信対象はテキスト、実行設定、状態およびベクトルとし、画像データは渡さない。

ワーカー異常終了時は実行中ジョブを失敗または再試行待ちにし、再起動できるようにする。短時間に繰り返し異常終了する場合は自動再起動を停止し、ユーザーへ通知する。

## 6. 推論処理

ruri-v3の推奨方式に従い、検索クエリと検索文書を区別する。

```text
検索クエリ: ユーザーが入力した自然言語
検索文書: 画像から構築した検索用文章
```

処理手順:

1. モデルマニフェストで定義した接頭辞を付加する
2. tokenizerでトークン化する
3. ONNX Runtimeで推論する
4. attention maskを考慮してmean poolingする
5. L2正規化する
6. 文書ベクトルはSQLiteへコミットする
7. USearchインデックスへ反映する

接頭辞、pooling、正規化等はユーザー任意設定にせず、モデルマニフェストへ固定する。

過度に長い画像メタデータをそのまま入力しない。最大トークン数と各情報源の採用上限を設定し、キャプション、タグ、Positive prompt、メモ、EXIF等を決定的な規則で検索文書へ構成する。

## 7. ジョブ優先度

推論ジョブは以下の優先順位を基本とする。

1. ユーザーが入力した検索クエリ
2. 現在表示中または編集中の画像
3. 新規追加画像
4. 既存ライブラリの初回処理
5. 再生成および全件再構築

文書はバッチ推論し、検索クエリは1件ですぐ処理する。一括処理中でも、バッチ境界で検索クエリを割り込ませる。

バッチサイズ、スレッド数、最大CPU使用率は実測に基づいて決定し、詳細設定で調整可能にする余地を設ける。

## 8. モデルのロードとメモリ

- 自然言語検索または埋め込みジョブ開始時にモデルをロードする
- バックグラウンド処理中はロード状態を維持する
- 一定時間未使用ならアンロード可能にする
- 「常にメモリへ保持」を詳細設定として提供可能にする
- メモリ不足を検出した場合はバッチサイズ縮小またはアンロードを行う
- 起動時の自動ロードは既定で無効とする

モデルロード中もキーワード、タグ、条件検索は実行可能とし、意味検索結果だけを準備完了後に追加できるようにする。

## 9. 実行デバイス

MVPではCPU実行を正式対応とする。

将来候補:

- Windows DirectML
- macOS CoreML
- NVIDIA CUDA
- その他ONNX Runtime execution provider

アクセラレーターが初期化できなかった場合は、状態をユーザーへ表示した上でCPUへフォールバックする。サイレントなフォールバックで実行デバイス表示が誤ることを避ける。

## 10. モデル変更

異なるモデル、revisionまたは次元数のベクトルを同一インデックスへ混在させない。

モデル変更手順:

1. 新モデルをダウンロードして検証する
2. 旧モデルと旧インデックスを維持する
3. 新モデルでバックグラウンド再埋め込みする
4. 新USearchインデックスを構築する
5. 完了後にアトミックに検索先を切り替える
6. ユーザー操作により旧モデルと旧ベクトルを削除する

切り替え途中も旧モデルによる自然言語検索を継続可能にする。

## 11. プロバイダー抽象化

埋め込み実行を共通インターフェースの背後へ置く。

```rust
trait EmbeddingProvider {
    fn model_info(&self) -> ModelInfo;
    async fn embed_query(&self, text: &str) -> Result<Vec<f32>>;
    async fn embed_documents(
        &self,
        texts: &[String],
    ) -> Result<Vec<Vec<f32>>>;
}
```

初期実装:

- `RuriOnnxProvider`

将来実装:

- OpenAI互換`/v1/embeddings`
- その他ローカル埋め込みモデル

プロバイダーはモデル情報、次元数、距離関数、接頭辞等を明示し、検索インデックスとの互換性を検証する。

## 12. 技術検証項目

- 30mおよび70mのONNX変換再現性
- 公式SentenceTransformers実装との出力誤差
- tokenizer、mean pooling、L2正規化の一致
- WindowsおよびLinux CPUでのロード時間
- 1件の検索クエリのレイテンシ
- 文書バッチ処理のスループット
- メモリ使用量
- 推論中のUI応答性
- キャンセルとワーカー再起動
- モデル変更中の旧検索継続
- ダウンロード中断、チェックサム不一致、容量不足
- ONNX Runtimeのクロスプラットフォーム配布
