# GEN-TO データモデル草案

- 文書状態: Draft
- 作成日: 2026-08-28
- 関連文書: [仕様草案](./spec-draft.md)

## 1. 基本方針

- SQLiteをアプリケーションデータの正本とする
- 画像本体はSQLiteへ格納しない
- サムネイルとベクトル検索インデックスは再生成可能な外部キャッシュとする
- 埋め込みベクトル自体は、インデックス再構築のためSQLiteにも保存する
- ファイル実体と画像内容を分離する
- 同一バイト内容のファイルでは、タグ、評価、キャプション、選別状態、コレクション所属を共有する
- DB内部の参照には整数ID、バックアップと移行にはUUIDを使用する
- ファイルが見つからなくなってもレコードを即時削除せず、不在状態として保持する
- AI処理は成功結果だけでなく、失敗と再試行の履歴も保持する

## 2. エンティティ関係

```text
LibraryRoot
  └── File
        └── Asset
              ├── AssetTag ── Tag
              ├── Caption
              ├── AssetMetadata
              ├── CollectionItem ── Collection
              ├── AiRun
              ├── Embedding
              └── Thumbnail

AiProfile
  └── AiRun

Job
FileOperation
```

### 2.1 Asset

画像内容を表す。MVPではファイルのバイト列ハッシュが一致するものを同一Assetとする。

メタデータだけが異なるPNGは別Assetになる。ピクセル一致および視覚的類似によるグループ化は将来機能とする。

主な属性:

- 内部整数ID
- UUID
- 内容ハッシュとアルゴリズム
- ハッシュ計算状態
- MIME type
- ファイル容量
- 幅、高さ、ビット深度
- アルファチャンネルの有無
- アニメーションの有無、フレーム数、再生時間
- 星評価
- 選別状態
- お気に入り
- 作成日時、更新日時

選別状態は以下とする。

- `unselected`
- `picked`
- `rejected`

星評価は0から5とする。

### 2.2 File

ファイルシステム上の個別ファイルを表す。複数のFileが同じAssetを参照できる。

主な属性:

- 内部整数ID
- UUID
- 登録ルートID
- Asset ID
- 登録ルートからの相対パス
- 表示用ファイル名
- 拡張子
- ファイル容量
- 更新日時、作成日時
- 利用可能な場合はOS固有のファイル識別子
- スキャン状態
- 最終確認日時

Linux等の非UTF-8パスを考慮し、表示用文字列とは別にOSネイティブのパス表現を復元できる値を保持する余地を設ける。

スキャン状態の初期案:

- `present`
- `missing`
- `unreadable`
- `unsupported`
- `corrupt`

### 2.3 LibraryRoot

拡張機能を有効にする登録ルートを表す。

主な属性:

- 内部整数ID
- UUID
- 表示用パスとOSネイティブパス
- 有効状態
- フォルダ監視設定
- AI自動処理設定
- EXIFおよびGPS送信設定
- 作成日時、更新日時

詳細なAI設定はAiProfileとの関連または専用設定へ分離する。

## 3. ID

各主要エンティティは、原則として以下を持つ。

```text
id    INTEGER PRIMARY KEY
uuid  TEXT NOT NULL UNIQUE
```

- `id`: SQLite内のJOINとインデックス用
- `uuid`: JSONLバックアップ、復元、別DBへの移行用

UUIDの具体的な形式とSQLite内の格納形式は実装時に決定する。

## 4. タグ

### 4.1 Tag

主な属性:

- ID、UUID
- 表示名
- 正規化名
- 任意のカテゴリ
- 作成日時、更新日時

正規化名には、少なくとも前後空白および検索上不要な表記差を正規化した値を保持する。大文字小文字、Unicode正規化、全角半角の扱いは実装前に規則を確定する。

タグの別名は`TagAlias`として追加可能にする。

### 4.2 AssetTag

AssetとTagの多対多関係を表す。

主な属性:

- Asset ID
- Tag ID
- 由来
- AI信頼度
- AI実行ID
- 手動編集済み状態
- 作成日時

由来の初期値:

- `manual`
- `ai`
- `import`
- `embedded_metadata`

AIで自動採用されたタグは通常検索の正式タグとして扱う。ユーザーが手動で編集した状態は、AI再生成時に保護する。

## 5. キャプション

キャプションは用途ごとに複数保持し、Assetへ紐付ける。

主な属性:

- ID、UUID
- Asset ID
- 種別
- 本文
- 由来
- 言語
- AI実行ID
- 現行状態
- 手動編集済み状態
- 作成日時、更新日時

種別の初期案:

- `description`: 自然言語検索用の説明
- `sd_tags`: 順序を持つSD学習用タグ列
- `user_note`: ユーザーメモ
- `ocr`: 将来のOCR
- `embedded_prompt`: PNG内のPositive prompt
- `embedded_negative_prompt`: PNG内のNegative prompt

再生成時は旧レコードを即時削除せず、非現行状態として履歴を残す。手動編集済みの現行レコードは自動で置き換えない。

SD学習用タグは、MVP初期ではキャプション本文として保持できる。タグ単位の一括編集が必要になった時点で、順序を持つ`SdCaptionItem`へ分解する。

## 6. メタデータ

検索頻度が高い項目は正規化した列へ格納し、それ以外の生データはJSONまたは圧縮BLOBとして保持する。

正規化候補:

- 撮影日時
- カメラメーカー、カメラ、レンズ
- GPS
- Orientation
- 生成ツール
- 生成モデル、VAE
- Sampler、Scheduler
- Steps、CFG scale、Seed
- Positive prompt、Negative prompt
- LoRA等の主要生成情報

生データ候補:

- EXIF JSON
- IPTC JSON
- PNG metadata JSON
- ComfyUI workflow JSON

Seedは生成ツールによる表現差と数値範囲を考慮し、文字列として保持する。

メタデータにはパーサー名とパーサーバージョンを記録し、パーサー更新時に対象データを再解析できるようにする。

## 7. コレクション

Collectionは以下の種別を持つ。

- `manual`
- `smart`

手動コレクションは`CollectionItem`を介してAssetへ紐付ける。項目は任意の並び順とコレクション内メモを保持できる。

スマートコレクションは構造化した検索条件をJSONで保持する。SQL文そのものは保存しない。

## 8. AI

### 8.1 AiProfile

OpenAI互換エンドポイントの接続設定を表す。

主な属性:

- ID、UUID
- 表示名
- Base URL
- モデル名
- APIキーの資格情報ストア参照
- Vision対応
- タイムアウト
- 同時実行数
- 追加設定JSON
- 作成日時、更新日時

APIキーそのものはSQLiteへ保存しない。

### 8.2 AiRun

個別Assetに対するAI処理の実行履歴を表す。

主な属性:

- ID、UUID
- Asset ID
- AiProfile ID
- 操作種別
- 状態
- プロンプトバージョン
- リクエスト情報
- 元応答
- エラー
- 開始、完了、作成日時

操作種別の初期案:

- `caption`
- `tags`
- `caption_and_tags`
- `embedding`
- `rag`

再試行の履歴を失わないよう、試行ごとの記録を残す。

### 8.3 Job

アプリ終了後も処理を再開できるよう、バックグラウンドジョブはSQLiteへ永続化する。

主な属性:

- ID、UUID
- ジョブ種別
- 対象種別と対象ID
- 状態と優先度
- 試行回数と最大試行回数
- ペイロードJSON
- エラー
- 予定、開始、完了、作成日時

## 9. テキスト検索

SQLite FTS5を使用し、Asset単位に統合した検索文書を構築する。

検索文書の候補:

- ファイル名
- パス
- タグ
- キャプション
- Positive prompt
- ユーザーメモ
- 検索利用が適切な正規化メタデータ

Negative promptとComfyUI workflow全体は意味検索文書には含めないが、明示的な全文検索の対象にできる。

複雑なDBトリガーだけに依存せず、Rust側の検索文書再構築ジョブでFTSを更新する。タグやキャプション等が変わった場合は対象Assetだけを再構築する。

## 10. 埋め込みとベクトル検索

モデルの取得、実行、ワーカー構成および更新手順は、[埋め込みモデル実行・配布方針](./embedding-runtime.md)に定義する。

Embeddingは以下を保持する。

- Asset ID
- 用途
- モデル名とリビジョン
- 次元数
- データ型
- 元検索文書のハッシュ
- ベクトル
- 作成日時

元検索文書のハッシュが現在値と一致しなくなった場合は、埋め込みを期限切れとして再生成する。

```text
SQLite内のEmbedding
  └── USearch HNSWインデックス
```

- SQLite内のベクトル: 正本
- USearch HNSWインデックス: 通常の高速検索に使う再生成可能な外部キャッシュ
- インデックス破損時: SQLiteから再構築
- USearchを利用できない場合: Rust実装による全件の正確検索へフォールバック

ベクトル検索は共通インターフェースの背後に実装し、少なくともUSearch HNSWとRustによる正確検索を交換可能にする。インデックスファイルはモデル名、モデルリビジョン、次元数、距離関数等を識別できるメタデータを持ち、SQLite内のEmbeddingと不整合になった場合は再構築する。

距離関数は埋め込みモデルの推奨に従う。コサイン類似度を使う場合は、保存時または検索時の正規化規則を統一する。

FAISSはMVPでは採用しない。将来、数百万件規模、GPU検索、またはUSearchでは不足する高度なインデックス方式が必要になった場合の候補とする。

SQLite公式のVec1は性能比較の候補に残すが、新しい技術であるためMVPの主要バックエンドにはしない。Qdrant等の独立したベクトルDBは、SQLiteとの二重管理を避けるため採用しない。

### 10.1 インデックス更新

- 新しい埋め込みをSQLiteへコミットしてからインデックスへ追加する
- 削除および更新もSQLiteを先に確定する
- インデックス更新に失敗した場合は、再構築待ち状態を記録する
- Asset IDの内部整数IDをUSearchのキーとして利用する
- モデルまたは次元数が異なる埋め込みは同じインデックスへ混在させない
- 大量更新後は必要に応じてインデックスを再構築または最適化する
- アプリ異常終了後はSQLiteとの世代情報を比較し、不整合なら差分反映または再構築する

## 11. サムネイル

サムネイル本体はSQLiteへ格納せず、外部キャッシュへ保存する。DBには以下を記録する。

- Asset ID
- サイズクラス
- 元画像ハッシュ
- キャッシュキー
- 幅、高さ、容量
- 最終アクセス日時
- 作成日時

サイズクラスの初期案:

- `small`
- `medium`
- `large`
- `preview`

キャッシュキーの先頭数文字でディレクトリを分散し、単一ディレクトリへのファイル集中を避ける。

## 12. ファイル操作履歴

Undoと障害調査のため、アプリ内ファイル操作を`FileOperation`へ記録する。

主な属性:

- ID、UUID
- 操作種別
- 状態
- Undo可能状態
- リクエストJSON
- 結果JSON
- 作成日時
- Undo実行日時

複数ファイルへの一括操作は1つの論理操作として記録し、ファイル単位の成功と失敗を結果へ含める。

## 13. SQLite運用

- WALモードを使用する
- 外部キー制約を有効化する
- DB書き込みをRust側へ集約する
- 読み取り接続と書き込み接続を分離する
- 長時間トランザクションを避ける
- スキャン、メタデータ抽出、AI処理は小さなバッチでコミットする
- スキーマバージョンとマイグレーションを管理する
- サムネイルや外部インデックスの破損をDB破損として扱わない
- DBバックアップ中も可能な範囲で閲覧を継続する
