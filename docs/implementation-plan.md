## 1. この計画の目的

Tauri 2、Svelte 5、TypeScriptおよび独立したRustコアで、GEN-TOの中核となる高速画像一覧、単一画像ビューア、2枚・4枚比較を実現可能か検証する。

本計画の完了条件は製品MVPの完成ではない。以下を実測し、採用予定の技術構成を正式決定できる状態にすることを目的とする。

- 数万件規模の仮想スクロール
- Rustによる画像走査とサムネイル生成
- RustからWebViewへの効率的かつ安全な画像配信
- キャッシュ済み画像の高速な連続表示
- 2枚・4枚比較と同期ズーム・パン
- バックグラウンド処理中のUI応答性

## 2. 実装上の固定事項

実装担当は、明確な問題が見つからない限り以下を前提とする。

- デスクトップシェル: Tauri 2
- フロントエンド: Svelte 5、TypeScript、Vite
- バックエンド: Rust
- リポジトリ構成: Cargo workspace
- 初期対象OS: 現在のLinux開発機
- 実画像: `sample/dataset`
- 仮想カタログ規模: 50,000件
- 初期対象形式: PNGのみ
- 一覧: 一定セルサイズのグリッド
- virtualizer: TanStack Virtualを第一候補
- 画像配信: Tauriの制限付きローカルプロトコル
- 画像バイト列をJSON、Base64、通常のcommand応答で渡さない
- サムネイル候補: 長辺256px、512px
- preview候補: 長辺2,048px
- サムネイル形式の第一候補: WebP
- プロトタイプのキャッシュ上限: 2GiB
- 完成版SQLite、AI、タグ、ファイル操作は実装しない

## 4. データセット

`sample/dataset`は現時点で以下の内容を持つ。

- 1,615 PNG
- 約957MiB
- 最大3,840×2,048
- 最大約7.9MP
- 最大ファイル約12.1MiB

### 4.1 リポジトリ管理

実装開始時に`sample/dataset/`を`.gitignore`へ追加する。データセット内のファイルを移動、改名、編集、削除しない。

データセットが存在しない環境でも、アプリ起動と単体テストが失敗しないようにする。ディレクトリは実行時設定または開発用引数で指定可能にする。

### 4.2 仮想カタログ

5万件のUI検証では画像ファイルを複製しない。1,615件を循環参照する仮想レコードをメモリ上に生成する。

各仮想レコードは以下を持つ。

- 一意な64bit ID
- 参照元画像IDまたはパス
- 仮想表示名
- 幅、高さ
- サムネイル状態
- 選択状態
- 仮の評価
- 仮の採用・除外状態

仮想カタログはUI負荷試験専用とし、実ファイル走査性能の結果と混同しない。

## 6. 共通実装規則

- Tauri固有型を`gento-core`と`gento-image`へ入れない
- ファイルI/Oと画像デコードをUIスレッドで実行しない
- パスを文字列連結で解決しない
- commandで巨大配列や画像バイト列を返さない
- 非同期処理に上限なしのspawnを使用しない
- デコードとサムネイル生成には上限付きワーカープールを使用する
- 画面外要求を低優先度化またはキャンセル可能にする
- キャッシュファイルは一時ファイルへ書き、成功後に置き換える
- panicを通常のエラー処理として使わない
- エラーはファイル単位で隔離し、一覧全体を失敗させない
- 計測用コードを主要処理経路へ組み込む
- プロトタイプであっても、ローカルプロトコルから任意パスを読めないようにする

## 9. フェーズ2: ディレクトリ走査とカタログ

### 作業

1. PNGファイルの列挙を実装する
2. ファイル容量と更新日時を取得する
3. 画像全体をデコードせず、可能な範囲で幅と高さを取得する
4. 安定した一覧順序を定義する
5. Rust側にカタログを保持する
6. ページ単位取得commandを作る
7. 走査進捗と個別エラーをUIへ通知する
8. 仮想5万件カタログを切り替え可能にする

### DTO候補

```ts
type ImageListItem = {
  id: string;
  displayName: string;
  width: number | null;
  height: number | null;
  byteSize: number;
  state: "ready" | "unreadable" | "unsupported" | "corrupt";
  thumbnailState: "missing" | "queued" | "ready" | "failed";
};
```

IDはJavaScriptの安全な整数範囲の問題を避けるため、IPC DTOでは文字列として渡す案を優先する。

### ページング候補

- 1ページ: 200～500件で比較
- UIは必要範囲の前後ページを取得
- Rust側の5万件全体を一括JSON化しない
- ページ要求には世代IDを含め、古い検索・フォルダ結果を破棄できるようにする

### テスト

- 空ディレクトリ
- 存在しないディレクトリ
- 読み取り不能項目
- PNG以外の無視
- 安定した並び順
- ページ境界
- 5万件カタログ

### 受け入れ条件

- `sample/dataset`を走査できる
- 走査完了前でも取得済みの項目を表示できる
- 5万件をフロントエンドへ一括転送しない
- 個別エラーで走査全体が停止しない
- 走査時間とメモリを記録できる

## 10. フェーズ3: 仮想サムネイルグリッド

### 作業

1. 一定セルサイズのグリッドを実装する
2. TanStack Virtualを用いて行を仮想化する
3. ウィンドウ幅から列数を算出する
4. サムネイルサイズ変更でセルサイズと列数を更新する
5. overscanを調整可能にする
6. プレースホルダーを表示する
7. 単一選択、Ctrl選択、Shift範囲選択を実装する
8. キーボード上下左右移動を実装する
9. スクロール位置を保存・復元する
10. DOM件数と表示範囲を開発用パネルへ表示する

### 注意事項

- 5万件分のSvelte componentを生成しない
- 項目IDをkeyに使用し、配列indexだけに依存しない
- 選択集合を全項目のリアクティブオブジェクトへ埋め込まない
- スクロール中に同期的なRust commandを大量発行しない
- ResizeObserver等から更新ループを作らない

### 受け入れ条件

- 5万件カタログを高速スクロールできる
- DOM件数が表示範囲とoverscanに比例する
- 選択変更でグリッド全体が不要に再構築されない
- サムネイルサイズ変更後も操作できる
- キーボード選択が画面外へ移動した場合に追従する
- スクロール位置を復元できる

### 判断ゲートA

ここで仮想スクロールに重大な問題がある場合は、以下を順に検討する。

1. TanStack Virtualの設定とSvelte状態分割を改善
2. TanStack Virtual coreを直接使用
3. グリッド部分だけを命令的DOM更新へ変更
4. Tauri／Svelte構成そのものを再評価

問題を隠すためにDOM全件生成へ戻さない。

### 作業

1. 画像デコードライブラリを確定する
2. 長辺256px、512pxのサムネイルを生成する
3. 長辺2,048pxのpreviewを生成する
4. WebPで保存する
5. 透過画像の扱いを確認する
6. キャッシュキーを実装する
7. キャッシュディレクトリを分散する
8. 一時ファイルとアトミック配置を実装する

10. 同一キーの重複ジョブを統合する
11. 優先度付きキューを実装する

### キャッシュキー

最低限、以下を含める。

- 元ファイルの検証可能な識別値
- ファイル容量
- 更新日時
- サイズクラス
- 生成アルゴリズムバージョン
- Orientation等、出力へ影響する設定

技術検証初期では全ファイルの内容ハッシュを必須にしなくてよい。ただし将来のAssetハッシュへ置き換え可能なAPIにする。

### キュー優先度

1. 単一ビューアまたは比較表示中
2. 一覧の表示範囲
3. 閲覧方向の先読み
4. overscan
5. 現在フォルダの残り

### 受け入れ条件

- UIスレッドを止めずにサムネイルを生成できる
- 2回目の表示ではキャッシュを利用する
- 同じサムネイルを同時に複数生成しない
- キャッシュ途中ファイルを正常データとして読まない
- キャッシュを全削除しても再生成できる
- 生成時間、容量、キャッシュヒット率を記録できる
- WebPが不適切なら、計測根拠と代替形式を記録する

## 12. フェーズ5: ローカル画像プロトコル

### 作業

1. サムネイル取得用プロトコルを登録する
2. preview取得用プロトコルを登録する
3. Asset IDとサイズクラスから許可済みキャッシュへ解決する
4. 未生成時の挙動を定義する
5. MIME typeとキャッシュヘッダーを設定する
6. パストラバーサルと任意パス読み取りをテストする
7. 応答時間と転送量を記録する

URL案:

```text
gento-thumb://asset/{id}/{size_class}?v={cache_generation}
gento-preview://asset/{id}?v={cache_generation}
```

TauriまたはWebViewの制約でscheme形式を変更する場合も、URLから任意パスを指定できない原則は維持する。

### 未生成時

初期案:

1. UIはプレースホルダーを表示
2. 可視範囲のIDをまとめてRustへ通知
3. Rustが生成キューへ登録
4. 完了イベントで対象IDとcache generationを通知
5. UIがURLを更新して再取得

プロトコルリクエスト自体を長時間ブロックして生成完了を待たせない。

### 受け入れ条件

- Base64を使わずにサムネイルを表示できる
- 許可されていないローカルファイルを取得できない
- 未生成サムネイルが完成後に表示へ切り替わる
- スクロール中の大量要求が無制限に残らない
- キャッシュ更新後に古いWebViewキャッシュを誤表示しない

## 13. フェーズ6: 単一画像ビューア

### 作業

1. 選択画像をpreviewで表示する
2. 前後移動を実装する
3. 次・前画像を先読みする
4. 画面内フィットを実装する
5. 原寸表示を実装する
6. マウス位置中心のズームを実装する
7. パンを実装する
8. ビュー状態のリセットを実装する
9. 連続入力時の古い要求を破棄する
10. 表示準備時間を計測する

### 状態案

```ts
type ViewTransform = {
  scale: number;
  centerX: number; // 0.0 .. 1.0
  centerY: number; // 0.0 .. 1.0
  mode: "fit" | "actual" | "custom";
};
```

`centerX`と`centerY`は画像内の正規化座標とし、比較表示へ再利用する。

### 受け入れ条件

- キャッシュ済み画像の連続移動で目立つ空白を極力生じさせない
- キーリピート時に最後に選択された画像へ追従する
- 古い画像のロード完了で現在画像を上書きしない
- ズーム中心が大きくずれない
- fit、actual、customを往復できる
- 先読みの有無による差を計測できる

## 14. フェーズ7: 2枚・4枚比較

### 作業

1. 比較スロットモデルを作成する
2. 2枚レイアウトを実装する
3. 4枚レイアウトを実装する
4. 操作対象スロットを切り替える
5. 基準スロットを固定する
6. スロットごとに画像を入れ替える
7. 同期ズーム・パンを実装する
8. 同期を一時解除できるようにする
9. 選択スロットだけ高解像度へ昇格可能にする
10. フレーム時間とメモリを計測する

### 同期規則

- 画像内の正規化中心座標を共有する
- 基本倍率は「fitに対する倍率」として共有する案を優先する
- アスペクト比が異なる場合も画像外へ過度に移動しないようクランプする
- スロットごとの一時的な同期解除状態を保持する

### 受け入れ条件

- 2枚と4枚を切り替えられる
- 画像サイズが異なっても概ね同じ相対位置を比較できる
- 4枚すべてを無条件に原寸展開しない
- 比較対象を変更してもUIが長時間停止しない
- 既存画像を新画像準備前に不必要に消さない
- 同期ON/OFFが予測可能に動作する

## 17. テスト方針

### Rust単体テスト

- キャッシュキーの決定性
- パス検証
- ページング
- 仮想カタログID
- 優先度順序
- 重複ジョブ統合
- 一時ファイル処理
- 画像情報取得失敗

### フロントエンド単体テスト

- 選択集合
- Shift範囲選択
- キーボード移動
- 列数変更
- ViewTransform
- 比較同期計算
- 古い非同期応答の破棄

### 統合テスト

- Rustカタログからページ取得
- ローカルプロトコルの許可・拒否
- サムネイル生成から表示まで
- キャッシュ削除後の再生成
- 高速な選択変更

### 手動検証

- スクロールの体感
- 連続画像送り
- マウス位置中心ズーム
- 同期パン
- 2枚・4枚比較
- ウィンドウリサイズ
- 表示倍率の変更

## 19. 既知のリスク

### WebView差

初期検証はLinuxだけなので、Windows WebView2とmacOS WKWebViewで同じ性能になるとは限らない。初期PASSはLinux上の方式成立だけを意味する。

### データセット偏り

現データセットはPNGのみで最大約7.9MPである。形式互換性、アニメーション、巨大画像の成立を証明しない。

### 強力な開発機

CPU、メモリ、GPUが一般的な最低動作環境より強力である。無制限な並列化や巨大なメモリキャッシュで問題を隠さない。

### WebP生成コスト

WebPの圧縮コストが初回サムネイル生成を遅くする可能性がある。JPEG、PNG、低圧縮WebPとの比較結果を残す。

### WebViewキャッシュ

同じURLで画像内容を置き換えると、古い画像を表示する可能性がある。URLへcache generationを含める。

### 非同期競合

高速に選択を変えた際、古い読み込み完了が現在画像を上書きする可能性がある。世代IDまたはrequest IDで破棄する。
